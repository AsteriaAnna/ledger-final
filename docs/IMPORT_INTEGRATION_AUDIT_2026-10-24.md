## 4. 按M1–M5分块审查

### M1 身份与关系

现有原则正确：当前用户来自服务端认证，绑定对象只读，导入不能写对象账本。本轮不新增登录、邀请或关系产品流程。

**A13 / P1：跨资源授权检查要落到接口约束。** API§2、§7.3/7.4/7.6已有部分描述，但应统一要求：batch、source_record、profile、mapping、account、existing_transaction均属于当前会话允许写入的本人范围，且source_record确属当前批次或其授权关联观察。不能只验batch归属后信任其他ID。对view=partner开放普通账单不等于开放原始文件、对方账号和导入记录；这些原始证据当前只给本人。验收伪造任一资源ID均无写入，并且不返回他人的原始字段。

### M2 账户与资金归属

**A01 / P0（与M3共享）：入账顺序有了，缺口金额来源没有。** 业务§3.6、§4.3和模型§6.2要求统一回补，但模型中没有“应该保有多少存款”的基准。仅给当前份额无法判断该补对象存款多少。例：对象存款当前100元，原先可能就是100元，也可能从300元被使用了200元；同样的当前状态对应不同退款分配。不能用账户初始份额硬当永远目标，也不能静默改成全进本人流动资金。最小决策是在已有资金机制中定义可用的缺口依据，或由用户明确接受更简单的默认入账分配；无需恢复逐笔退款原单关联。此项也影响原有“支出金额减少补缺口”的实现，不只是退款。

**A14 / P1（与M3共享）：起始日切换及撤销影响不能留下负份额。** 业务§3.1/4.3与API§6.4已承认改日期跨起始日会改变余额。若退款到账后已被后续交易使用，再把退款改至起始日前、减少金额、改到账账户或删除，撤销旧影响可能使当前份额不足。现有“不重算后续交易”和“原子失败”可以沿用，但要明确整笔拒绝的校验点与错误反馈，不能只改日期。沿用FUNDS_ALLOCATION_NOT_POSSIBLE或适当明确边界，不擅自新增透支功能。退回日期只为改统计、还是同时改账务日期，当前已按后者设计；本轮不擅自增加第二个统计日期来改掉它。

### M3 交易账务

M3继续是唯一写入入口；M4只能提交经过校验的候选命令，不能复制支出/退款份额算法。A01、A09和A14是M3接入对应能力的前提。

**A08 / P1：refund的账务语义与编辑白名单未完整定义。** API§6.1的accounting_semantics只列ordinary（收入/支出）、credit_purchase、credit_repayment、internal_transfer，没有定义refund使用哪种合法组合。§6.4又泛允许把类型改为收入/支出/转账，与“官方退款类型不可混淆、退款不计普通收入”可能发生冲突。需要一张明确组合表：退款语义取既有ordinary的扩展还是新增受控refund语义，哪种都只是候选；不允许实现者猜。明确refund_kind为来源识别、affects_spending为可编辑布尔；非refund字段应拒绝或按明确规则清空；null、字符串“false”、修改source_occurred_at应有明确422结果。补充退款PATCH请求和详情响应示例，带version和受影响月份，源字段只读。

### M4 导入与来源证据

**A02 / P0：退款待处理后没有合法的恢复创建路径。** API§7.4第660行仍说create_transaction只用于普通收入、支出、转账；第661行却允许退款账户不明进入通用待处理。复现：退款读出→账户不明→用户完成映射→目前无明确合法调用创建退款。最小补充：允许服务端依据已识别官方退款来源恢复创建refund；客户端仍不能POST手动新建退款，也不提交原消费ID。映射完成后需要明确resume/reprocess动作及响应，复用已有resolution即可，不必设计新异常中心。link_existing_transaction若用于退款，只能关联同一退款事件的refund，不可关联原expense。

**A03 / P0：缺少可展示的逐行结果DTO与互斥结果计数。** API§7.1只有计数、review_items里的ID/原因码，§7.3只有文字说明；用户要求展示“读到了什么、为什么这样判断”，当前客户端无明确稳定结构。现有示例声明169行，created120+linked8+duplicate3+review1+failed0=132行，其余37行无分类说明；核对项不是来源行，不能拿来补齐。要补逐行结果与分页、原始证据/候选/正式transaction_id/原因码，以及排除、不生效、待处理、错误等结果计数。phase是处理阶段，disposition是最终行结果，不应拿单一状态混用。§7.2第5步“独立创建退款”还在去重/已有来源处理之前，应改为识别候选，真正创建统一放到来源检查后的M3步骤。

**A04 / P1：来源档案选择与映射完成后的用户路径不完整。** API§7.1、7.5支持首次创建档案、多候选选择，却没有档案列表或错误响应中的候选结构；零个候选、多个候选、识别冲突时前端如何得到ID、是否保留已上传文件与重试batch也未表达。最小补齐现有导入响应/错误详情，或补窄范围的来源档案查询；不要求每次导入都让用户再选一次。只存在一个档案时复用是既有产品选择，但不能声称昵称证明了账号身份。

**A05 / P0：同文件快捷跳过与删除后重导、待处理恢复冲突。** 模型§7.2、API§1.4/7.2允许相同文件直接识别已处理；同时要求删除后可重导。若缓存旧批次结果或发现SourceRecord存在就跳过，删除的交易永远无法恢复，映射刚补全的来源也可能永远跳过。应区分：同Idempotency-Key的网络重试返回原结果；用户发起新的导入操作（新键）要按当前来源关联状态检查。已关联有效交易→不重复入账；来源存在但当前交易为空→重新走M3；来源仍待处理→按新映射重新判断。文件相同只复用解析证据，不能永久封锁再次处理。

本轮直接探测旧实验的ingest_candidate：保留来源key、将transaction置空后重导，created=false且transaction_restored=false。原14项检查没有覆盖这一情况，删除测试实际上pop掉了整个内存来源项；因此“14项通过”不证明删除后重导。这是实验简化造成的明确限制，不能复制为生产逻辑。

**A06 / P0：完整覆盖范围不等于能够对所有手动交易作缺失结论。** 业务§5.6、模型§7.3和API§7.1/7.2仍可能只靠全量标签+时间+行数开启核对。存在四个实际风险：

1. 支付宝声明结束23:59:59，导出20:07:52；晚间尚未发生的交易不能被判缺失。需保存declared范围与实际可核对范围；保守上界不晚于导出时刻，精确边界适用条件仍需确认。
2. 本轮排除123行不等于那123行不存在。可提取其来源身份但暂不入账；其对应范围/语义不能被负向核对为缺失。必要时只禁用相关作用域，而非让整个文件永远不可读。
3. 同一银行卡可经微信或支付宝消费，手动记录仅有account_id不能证明应在微信文件出现。缺少平台/来源适用性信息时，不能把银行卡上所有未匹配手动交易都判为该平台漏记。
4. 用户编辑过的occurred_at不是官方source_occurred_at；已有来源的退款不能因记账日期改出/改入范围就重复产生缺失结论。

最小补充：把“结构读取完整”“本次支持范围”“具备缺失核对资格”分开判定，核对按可证明的平台账号、渠道、时间与交易语义作用域执行。coverage.complete不能同时含糊承担所有含义。

**A07 / P1：渠道映射的命名空间及规范化键不足。** 模型实体表和API§7.6主要按用户+platform+渠道字符串映射，没有清楚纳入来源档案。两个微信账号的“零钱”不是同一个账户；若均由一人导入，平台+零钱会串账。需要显式来源档案作用域（与全局银行卡映射的可复用边界），把状态推断的微信零钱也转为同一规范化键；原串“银行卡&闪购支付红包”应使用剥离优惠后的账户键，避免每种优惠重复映射。不同平台的银行卡可经确认指向同一个Account，不按尾号自动全局合并。改映射只影响待处理/新来源还是会追改已入账交易，也要明确，不能批量静默重写历史。

**A09 / P0（与M3共享）：52条转账候选不能直接写入transfer，提现费用与执行顺序未闭合。** 模型要求内部transfer两个账户等额相反，支付方式却在提现行代表目标银行卡；46条普通微信转账只证明一端方向，不能默认全为本人账户间转账。6条充值提现已有两端线索，3条提现备注出现手续费，可能需要“等额内部转账+独立费用”等最小表达，但必须先确认两端实际金额，不能现在冻结费用拆法。若未来同一经济转账在两平台各有一条来源，需要避免将同一转账的两端重复记成两笔；一笔Transaction可挂多SourceRecord是现有承载方向，具体匹配证据待验证。两份原表总体按新到旧排列，直接按表格顺序写账会改变流动/存款扣减结果；初次批量入账需明确时间顺序与同秒规则，不能把“不重算既有后续交易”理解为可以任意顺序导入。

**A11 / P1：来源状态更新不等于账务处理永远忽略。** API§7.2、模型§7.1允许最新观察更新当前状态，却未明确无交易的失败/处理中来源后来成功时如何处理。已有有效交易且仅等待收货→交易成功时，只更新证据不再入账（旧报告5条属于这种状态变化）；尚未创建交易且变为可入账时，应重新评估而非按来源存在跳过。涉及方向/金额等重要来源变化且已有用户编辑时，不静默覆盖，需要明确差异处理。旧文件不能覆盖新观察；相同导出时间冲突也应有确定处理。实验内存模型没有导出时间比较，不能验证此约束。

**A12 / P1：既有手动账单匹配仍未得到真实验证。** 取消退款原消费关联不等于取消“官方消费与同一笔手动消费”的来源匹配。业务§5.4、API§7.2/7.4尚无金额/时间/账户/方向/类型的接受条件与多候选规则；实验没有真实手动交易集合，不能给出匹配率。编辑后的日期和金额应与原始来源证据区分，SourceRecord已有关联时先走稳定关系；弱字段相似只产生候选。link_existing_transaction要校验同事件语义，不能把refund连到原消费，也不能跨用户或为了省确认而合并两笔同额消费。

**A15 / P1：实验输出不能直接作为生产DTO。** 实测所有338条时间无偏移，不符合API§1.1；minor允许0，而正式交易要求正整数；缺少account_id、category_code、accounting_semantics与真实档案；脚本没保留完整raw_fields/商户单号/备注与文件元数据；平台判型由CLI传入；状态主要用包含字符串判断，未知状态未按白名单停止。实验是样本断言与内存状态，不是HTTP/数据库实现；须增加转换层和未知情况明确结果。保留现有实验，不把其方法直接复制成正式M4。

### M5 预算与统计

**A10 / P1：日期、负净花销、舍入与输出字段需要统一。** IMPORT_RECOGNITION允许净花销为负，API§4.1仍只有month_spent等总数示例，未说明有符号字段、支出/退款分项、remaining可否大于预算、如何舍入日均与预测（整数分除自然日可能非整数）。需要按既定净花销口径表达，不能擅自把负数截断为0，也不能把退款计普通收入。切换历史月份、未来记账日期和截至as_of_date的筛选需明确，避免整月交易除以当月已过天数。上月日均为零仍保持既有非阻塞定位，不借这次审查扩展分析产品。更新同一退款日期/抵减开关后，对涉及月份的预算、日均、预测使用同一版本的交易事实。

## 5. 建议的接入契约形状（候选，不是已实现接口）

### 5.1 模块交接

| 交接点 | 生产者→消费者 | 输入/输出 | 缺失时怎样处理 |
|---|---|---|---|
| 授权 | M1→应用用例 | 当前user上下文、各资源可读写范围 | 拒绝，不让M4自行推导授权 |
| 来源账号/账户映射 | M4↔M2 | 原始账号快照、规范化渠道键→profile_id与account_id | 来源待处理；只向用户展示必要选择 |
| 识别完成 | M4→M3应用用例 | 已授权账户、金额、时间、最终type与语义、退款标记、自己的SourceRecord | 未具备条件的行不调用M3 |
| 账务提交 | M3→M4 | transaction_id、账户影响、份额结果、明确失败 | 同事务关联来源；失败不留下半笔账务 |
| 查询展示 | M3/M2→M5 | 已保存交易与有效资金结果 | 不让M5用候选推算另一套余额 |

无需新建M6退款模块、独立退款服务或第二套保存算法。

### 5.3 行结果与批次计数

建议每个来源行最终只归入一类：created、linked_existing、duplicate_existing、excluded、ineffective、needs_review、failed。已有来源观察状态更新是附加标记，不再多算一行。一次正常完成的解析批次，这七类数量之和应等于parsed_record_count；若批次异步处理中，另外明确尚未处理数量，不能伪装完成。

manual_transactions_not_found与reconciliation_items_rechecked按手动交易核对项计数，不纳入来源行总数等式。来源去重、同文件重试、状态变化、重新入账也应明确对应哪种最终结果。

本次实验可报告的守恒等式见§3，不能把146支出候选自动填进transactions_created。

### 5.4 待处理恢复路径

1. POST /imports保留已上传来源，返回batch与逐行结果；无明确来源档案时说明可恢复的候选/错误信息。
2. 完成档案/渠道到实际账户映射；不能直接写AccountFundMovement。
3. 对needs_review来源复用已有resolutions/重新处理机制，由后端从原始来源重新验证完整命令。
4. 官方refund允许在此路径经M3创建，不开放无来源的手动退款；成功返回自身transaction_id。
5. 重试保持幂等；已成功来源不重复创建；新批次可处理此前被删除或尚未成功的来源。

### 5.5 M3退款字段组合与PATCH（待确定的语义不伪造）

| 字段 | 规则 |
|---|---|
| type | refund，只能由官方来源创建 |
| refund_kind | merchant_refund或transfer_return，来源识别；与普通type严格区分 |
| affects_spending | 布尔；默认依子类型，可编辑；不影响账户流入额 |
| amount_minor | 正整数分；普通优惠退款按用户确认取实际金额；未知费用语义不硬套 |
| account_id | 当前用户可写的实际到账账户；Account映射完成后才提交 |
| occurred_at | 可编辑记账时间；带时区，默认官方时间 |
| source_occurred_at | M4只读来源时间，不能PATCH覆盖 |
| source_record_id/来源证明 | 服务端验证；客户端不能凭空制造合法refund |
| accounting_semantics | 当前枚举尚未容纳refund，需最小契约决策后明确；本报告不选择新枚举 |
| version | 并发编辑校验；金额与抵减更新不能互相覆盖 |

候选PATCH请求：

```json
{
  "occurred_at": "2026-08-15T12:00:00+08:00",
  "affects_spending": false,
  "version": 3
}
```

响应至少返回新交易version、记账时间、抵减设置、只读来源时间，以及受影响月份；若跨起始日，说明本笔applied/historical_only变化与账户结果。发生份额不足或并发冲突时整笔失败；不默默保存一半。

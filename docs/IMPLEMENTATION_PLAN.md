# 星账｜实施路线与验收任务

**版本：** v0.1  
**状态：** 候选实施计划，尚未开始功能代码实现  
**基线：** 核心业务规则 v2.5、逻辑数据模型 v0.2、API 契约 v0.1、工程模块边界 v0.1

本计划将设计阶段的结果转换为可拆分、可验收的开发任务。任务顺序优先建立最小可验证的完整业务路径，不以“先把所有底层做完”为由无限延迟可用功能，也不跳过会造成账务返工的必要约束。

## 2. 阶段 A：关闭设计前置项

### A1. 审阅 API 契约

- [x] 修正首页总览示例中的日均、变化率和月度预测算术。
- [x] 明确交易金额使用正整数分，账户影响/资金变动使用带符号金额。
- [x] 补充退款金额编辑不能套用普通支出差额逻辑。
- [ ] 确认退款到账账户与原消费账户不同时，资金份额如何恢复。
- [ ] 确认原交易是信用消费且无现金扣减份额时，退款如何分配。
- [ ] 明确修改账户记账起始日期时，如何原子重建该账户的交易影响与资金变动。
- [ ] 明确关系绑定凭据的生成、过期、验证和防重复使用方式。

验收：上述规则有明确决策记录；相关接口不依赖未写明的隐式假设。退款边界未确认前，可继续开发账户、普通收入/支出和不涉及退款的功能，但不得宣称退款路径已完整验收。

### A2. 确认工程模块边界

- [x] 将 M1–M5 映射到工程责任。
- [x] 明确交易写入统一入口。
- [x] 明确导入模块不能直接写资金变动。
- [x] 明确统计模块只读账务事实。
- [ ] 技术选型后，将逻辑边界映射为实际目录/接口；不要为每个实体机械地建目录。

验收：开发任务可以指定单一责任模块、依赖接口、允许修改范围和测试位置。

### A3. 做出必要的工程选型

需要在开始物理 Schema 和可运行服务之前决定：

- 客户端形态如何落地（响应式 Web、PWA、Android 壳或其他形式）；无论选哪种，首发必须具备完整可用的移动端记账体验。
- 前端框架、后端运行环境。
- 数据库及事务能力。
- 登录认证与服务端身份验证方式。
- 部署环境和必要的文件存储方案。
- 开源许可（若计划公开发布）。

验收：形成短小的技术决策记录，说明选项、选择理由、成本/限制和回退路径。未选定前不把任何具体技术写成既定事实。

## 3. 阶段 B：物理数据模型与最小工程骨架

任务：

1. 将逻辑实体映射为物理表/集合与字段。
2. 为用户归属、账户、交易、交易账户影响、资金变动、来源证据和预算定义主键、外键/关联约束、唯一约束及必要索引。
3. 明确金额整数分、日期时区、枚举、版本号与来源 ID 的持久化格式。
4. 建立可提交/回滚的 Unit of Work 或等价事务边界。
5. 建立服务端身份上下文、关系绑定的数据结构与资源归属检查。
6. 明确桌面端与 Android 端共用业务用例、API 契约和账务规则；平台差异留在客户端适配层。
7. 建立自动化测试入口与最小 CI；不先搭复杂部署流水线。

验收：

- 物理模型能映射逻辑数据模型的核心实体和关系。
- 当前用户 ID 来自已验证身份，不从请求体接受为授权依据。
- 账户余额和资金份额没有独立可写的第二份真相。
- 交易与资金变动能够原子提交/回滚。
- 双人只读权限在数据模型和服务端应用层中有明确承载，不留到 UI 完成后再补。

## 4. 阶段 C：第一个可运行垂直切片

目标：先做出一条真正可运行、可观察、可验收的路径，而不是先堆齐所有空模块。

包含：

1. 用户登录后的当前身份解析（采用阶段 A 选定的认证方案）。
2. 创建一个实际账户，设置起始日期、初始余额和资金份额。
3. 新建一笔普通支出或收入。
4. 查询交易详情、账户余额和资金份额。
5. 首页读取最小资金总览。
6. 发生校验失败时，保证数据未被部分写入。

验收场景：

- 创建初始余额 ¥5,000，初始份额合计必须恰好为 ¥5,000。
- 普通支出 ¥25.80 后，账户总额与资金份额都减少 ¥25.80，且份额扣减顺序正确。
- 普通收入 ¥10.00 后，自己的流动资金增加 ¥10.00。
- 把同一请求用同一个幂等键重试，不产生第二笔交易。
- 通过伪造他人 user ID 不能读取或修改未授权资源。
- 任何一次账务操作失败都不留下部分 Transaction 或 AccountFundMovement。

## 5. 阶段 D：交易生命周期与资金规则

按小任务依次完成：

1. 普通收入/支出及存款使用提醒。
2. 交易列表、搜索、筛选和详情。
3. 编辑交易字段与金额差额处理。
4. 删除交易及其账务影响。
5. 内部转账的双账户影响。
6. 真实退款与部分/多次退款。
7. 交易类型变更。
8. 历史交易、记账起始日期与余额影响状态。

验收：

- 每个任务均有成功、失败和重复提交测试。
- 转账两端影响金额相等、方向相反；不计收入或消费。
- 编辑交易只处理该交易，不自动重算后续交易。
- 删除消费时关联退款按冻结规则一并删除；来源证据可供重新导入。
- 退款累计金额不得超过原消费金额；退款资金分配遵循确认后的边界规则。
- 起始日前的交易可查询和统计，但不影响该账户起始日后的余额。
- 任何失败都不留下单边转账、超额退款或份额不守恒状态。

注意：第 6 项中涉及“退款到账账户不同”和“信用消费退款”的组合，必须在阶段 A1 决策完成后才验收。

## 6. 阶段 E：首页统计与预算

任务：

1. 实现首页资金与四类资金份额汇总。
2. 实现本月花销、自然日平均、上月日均、日均变化率和本月预计花销。
3. 实现个人月度预算创建/修改、剩余额度和超支提示。
4. 实现绑定后对象资金可见的查询聚合，但不混入当前用户消费和预算。

验收：

- 所有资金金额由统一账务事实和资金份额汇总。
- 退款关联后修正原消费月份，而不是退款发生月份。
- 内部转账与信用还款不重复计为消费。
- 对象消费不占用当前用户预算。
- 超支时返回正数超支额；未超支时返回剩余预算。
- 使用固定日期和固定交易数据测试日均、变化率、预测结果，避免示例和实现出现算术矛盾。

## 7. 阶段 F：微信/支付宝官方账单导入

先用真实官方账单样例验证字段，不先增加 AI 识别层。

任务：

1. 解析文件结构、平台、账户、交易 ID、时间、金额、交易状态、类型和退款字段。
2. 标准化交易记录，并记录无法支持或无法解析的行。
3. 建立来源账户映射，避免用户每次重复选择。
4. 将导入记录与手动交易、历史来源记录匹配。
5. 对确定的新交易调用统一交易用例；对已有交易只关联来源。
6. 处理退款关联、重复导入、用户删除后重新导入。
7. 展示新增、已关联、重复跳过、待处理和失败数量。
8. 保存导入批次与来源证据。

验收：

- 同一文件/同一幂等请求重复导入不重复入账。
- 已存在的同一笔手动交易可关联官方来源，不重复创建。
- 不稳定 ID 场景不只凭金额、日期、商户相同就静默合并。
- 退款不能静默关联到错误的原消费，也不能静默丢弃。
- 手动修正的重要字段不会被官方导入静默覆盖。
- 每种受支持交易状态都有明确处理结果。
- 使用真实微信、支付宝文件做逐行对照，记录新增、关联、跳过、异常的准确数量。

## 8. 阶段 G：双人绑定与对象只读查看

双人支持是首发核心范围，不是可选的远期增强。本阶段安排在账务核心可运行之后实施，但数据归属、关系模型和服务端权限检查必须从阶段 B 开始就存在；首发版本不能在未完成本阶段的情况下宣称达到完整产品验收。

本阶段交付用户可见的绑定流程，并让桌面端与 Android 端共用同一套服务端业务规则和数据。

任务：

1. 按阶段 A1 确认的凭据机制完成绑定。
2. 首页同屏展示双方四类资金。
3. 账户与账单提供查看对象数据的入口。
4. 对象的账户和交易仅只读；写接口必须由服务端拒绝。
5. 双方预算保持独立，不自动合并账单或虚构共同账户。

验收：

- 未绑定用户不能通过传入对方 ID 查看数据。
- 绑定后可以读取对象允许开放的账户/账单。
- 绑定后仍不能创建、编辑或删除对象数据。
- 双方资金份额按归属人与性质显示，不因保管关系混淆。
- 当前用户预算不包含对象消费。

## 9. 阶段 H：整体验收与交付

- 在真实手机视口/目标移动端上走通登录、账户选择、手动记账、账单查看与结果反馈；移动端核心流程不依赖截图识别。
- 验证桌面端与 Android 端调用相同业务能力时产生一致的账务结果。
- 按核心业务规则中的经典场景运行端到端测试。
- 对金额、退款、转账、起始日期、来源去重与权限边界进行回归。
- 检查错误反馈、加载/失败状态和重复提交体验。
- 确认 CI、构建、部署与最基本的运行说明。
- 更新 README、路线图与验收记录，只把真实运行通过的功能标记为完成。

## 10. AI 开发任务模板

每次只给一个可独立验收的小任务，并包含：

1. **目标：** 用户可观察到的变化或明确的底层约束。
2. **依据：** 相关业务规则、数据模型、API 和模块边界章节。
3. **允许修改范围：** 需要修改的模块和明确禁止触碰的区域。
4. **前置条件：** 依赖接口、未决规则和测试数据。
5. **验收标准：** 至少一个正常场景、一个失败场景；账务写操作还要验证原子性/幂等性。
6. **交付结果：** 修改文件、运行过的测试、未解决的问题与下一步。

不接受只说“实现完了”但没有修改清单、测试结果和已知限制的交付。

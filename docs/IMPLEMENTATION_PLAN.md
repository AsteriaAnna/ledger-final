# 星账｜实施计划与验证

本文件只保留当前状态、实施顺序和当前验证结果，不堆叠版本日志。[业务规则](BUSINESS_RULES_DISCUSSION.md)决定行为，[模块边界](ENGINEERING_MODULE_BOUNDARIES.md)决定责任，[模型](LOGICAL_DATA_MODEL.md)和[API](API_CONTRACT.md)表达同一契约。

## 1. 当前状态

已有六份核心设计文档及一个可运行的内存参考验证脚本；没有生产前后端、HTTP路由、数据库迁移或已部署应用。不能将文档或参考模型通过说成产品已实现。

M1–M5始终指业务模块。以下阶段用A–F编号，不与业务模块混用。当前文档范围已收敛；技术选型、持久化事务、真实鉴权与客户端仍需工程落实，不留下互相矛盾的业务备选稿。

## 2. 开发阶段

| 阶段 | 范围 | 验收出口 |

| C 交易生命周期 | M2分配/基准与起始状态；M3编辑删除、内部转账、独立退款；M5统计预算 | 当前份额非负、回补可计算、跨起始日安全、日期/抵减一致；无手动refund后门 |
| D 官方导入 | M4解析/证据/profile/映射、逐行结果、恢复/重导、必要匹配与核对，调用M3 | 真实文件逐行结果守恒；补映射可继续；删除保留来源后新操作可恢复；不支持行不造账 |

M1权限从阶段A/B贯穿；E不是后期补丁。技术选型前不把具体供应商写成既定事实。截图、负债、费用转账与解绑不纳入本次首发实现。

每个实现任务只指定一个主责模块、依赖接口、允许修改范围、输入样例和验收结果；跨模块原子事务由应用用例协调，不另造保存入口。

## 3. 当前流程验证

2026-10-24运行现有[参考脚本](../experiments/verify_import_recognition.py)，使用两份用户官方XLSX、固定北京时间时钟和虚构本人Account映射。原文件只读，不上传仓库，不写真实账户。

**107项参考规则/流程检查通过。** 它们检验的是文档行为、请求/响应示例和内存参考实现，不是生产实现、鉴权安全或数据库事务验收。包含版本/重试保护的参考分支仅验证候选语义，不表示D1–D3已由用户选定或已在生产开启。参考模型未保存手动分配的完整时间日志，因此含这类调整的起始重建会安全拒绝；生产实现需从有效movements重建，不能照搬该限制冒充全部支持。

部分规范（真实token、batch版本并发、持久化、分页、核对项持久生命周期、来源观察人工选择、客户端操作）仍须阶段A–F实现后运行验证。

### 3.1 经典动作

| 动作 | 验证输入/断言 |
|---|---|
| 支出跨三份额 | 流动100、本人存款100、对象存款100，支出250→剩对象存款50 |
| 独立退款回补 | 再退款120→补对象50、本人70，不需要原消费ID |
| 手动分配调整 | 同步改变基准与当前份额，回补上限可计算，不维护另一目标余额 |
| 支出金额减少 | 仅处理差额，先补当前缺口，再加流动资金 |
| 编辑退款抵减 | 账户/份额不变，净花销变化 |
| 改退款日期 | 不跨起始日保留份额计划；跨起始日切换历史/有效影响 |
| 类型变更 | 支出→内部转账→收入，保留交易ID；禁止普通类型改refund、refund改普通收入 |
| 起始状态修正 | 本账户重建历史/有效影响，其他账户不变；不安全重建整体拒绝 |
| 安全/不安全删除 | 删除仅撤销自身；资金已被使用时整笔拒绝并恢复快照 |
| 并发与非法输入 | 旧version、0/负金额、布尔金额、字符串false、未来日期、源时间写入均拒绝 |
| 本人与对象 | 虚构他人Account/profile无法进入写命令；真实身份验证仍未实现 |
| 转账 | 两端等额、不同账户、仅流动，起始日两端独立；平台转出可明确为支出 |
| 补映射恢复 | 同一官方退款先needs_review，补映射后使用原来源创建 |
| 退款来源关联 | 来源只连同一refund，禁止连原expense；同事件候选只提示，确认新事件才创建 |
| 删除后重导 | SourceRecord保留、transaction为空，新键导入恢复，不被来源存在或文件相同阻止 |
| 重试与用户编辑 | 同键不重复执行；新键重导保留用户日期/抵减；同键不同内容拒绝 |
| 状态观察 | 旧导出不覆盖较新事实，同时间冲突待处理；关闭来源后来有效可首次创建 |
| 原子写入 | 模拟来源关联失败，交易和余额回滚，来源观察可保留 |
| 统计算术 | 月花销3200/第20天→日均160、预测4960；预算3000→超支200；不提前舍入日均 |
| 负净花销 | 净额可负，预算剩余可大于预算；跨月抵减与零分母有确定输出 |
| 缺失核对资格 | 银行卡仅Account不够；明确profile且范围支持才可核对；已有来源/导出后时段不误判 |

试点新增检查覆盖：创建请求必填/条件字段与错误结构、整数金额/未知字段/缺时区拒绝、退款空改动不增版本、旧版本不能绕过空改动校验、PATCH省略/false/null区分、来源时间只读。并未验证实际HTTP头、真实超时或数据库提交；这些依赖用户选择后实现。

## 4. 工程实现后必须补的验证

- 用真实认证上下文验证对象只读、batch/source/profile/mapping/account/transaction的归属与相互关联，不能只相信参考模型的虚构owner。
- 对来源唯一约束、并发请求、幂等键生命周期、事务回滚、同文件解析复用和删除重导进行真实数据库验证。
- 对全部HTTP请求/响应、严格字段类型、分页、batch版本、profile选择和resolution刷新结果跑实际接口测试。
- 验证完整/不完整文件、覆盖范围与核对项保留/删除/后续匹配生命周期；原始信息不在只读对象接口泄露。
- 在手机与桌面走同一条用户路径，不因单元/参考验证通过就跳过可用性验收。

## 5. 写接口试点的能力选择（待用户确认）

API§4.2“创建交易”和§4.3“编辑退款”先做行为试点。以下不是运行时功能开关，不建设配置平台；用户选择后只保留选定行为，再转这两个接口的OpenAPI。没有确认前不编写依赖这些选择的生产写接口。

| 决策 | 不采用时会有什么具体问题 | 触发条件/概率证据 | 最小候选方案及新增复杂度 | 当前结论 |
|---|---|---|---|---|
| D1 创建请求重试保护 | 服务器已创建但响应丢失，用户再次POST可能再扣一次款；禁用按钮不能防网络重试 | 仅在已成功后的重复提交/结果未知重试触发；可用故障注入复现，暂无真实请求数据，不能给百分比 | 同一数据库保存本人+方法路径+键、规范化请求摘要、结果，建议保留24小时；处理同时到达的同键与过期键。增加一类记录、清理与验证；不需要Redis | 推荐，但待用户选；API已同时写出有/无保护的行为 |
| D2 实现“整笔成功或失败” | 交易已写、资金只改一半，或转账只改变一端，会违背既有业务规则 | 多项账务写入间异常/进程退出/并发争用会暴露；概率未知，正常请求不必然触发 | 推荐数据库自身事务与适当原生并发控制；须所选数据库支持，增加一次业务提交边界与故障/并发测试。不引入分布式锁、补偿队列 | 业务一致性要求保持；是否采用原生事务由用户选。不采用则需先证明另一简单方案可满足要求，否则暂不实现写入，不能静默接受半笔账 |
| D3 退款编辑版本比较 | 本人手机/电脑读同一旧值后改同一字段，后成功的请求可覆盖先前修改 | 仅本人多端/多标签同时编辑同一资源触发；对象只读不是第二写入人。暂无使用频率数据 | 在现有version上作条件更新，冲突返回409，客户端刷新；不需新组件/分布式锁。增加比较与冲突提示 | 推荐，但待用户选；不采用则明确后成功写入生效，不能声称防覆盖 |

D1候选的行为边界：作用域是本人+HTTP方法+路径+键；JSON字段顺序不影响相同请求判断，缺省字段按接口默认值补齐后比较；验证失败且未执行的请求不缓存为成功。建议24小时内相同键重放同结果，过期可视为新请求，因此过期后不能保证避免重复。若原交易随后被编辑/删除，旧键仍重放原操作结果（不是当前资源快照）；查当前状态要GET。此保留期限也是候选方案的一部分，不冒充用户已确认。

D2业务不变量与技术手段不同：可以选择不用某种事务技术，但不能同时声称“允许半笔成功”和“账务一致性不变”。两笔并发支出也必须满足非负份额，不能只做读检查再各自写入；由所选数据库的简单原生机制实现，不据此默认加分布式锁。

D3不负责网络成功结果的重放，也不代替D2的余额并发安全。PATCH只发送变化字段；没开版本比较仍可能同字段覆盖。参考脚本中的版本检查是一个候选行为的内存模拟，不表示生产能力已经开启。

可一次选择的推荐组合：**数据库原生事务/并发控制 + 创建请求单库幂等记录 + 编辑version比较**。更省状态的候选组合是数据库原生事务/并发控制加编辑version比较、暂不做创建幂等，接受POST结果未知时不能安全自动重试。用户也可逐项选择；不引入Redis、MQ或额外锁服务。无实际实现选型前，不新增这些依赖。

## 6. 契约格式的轻量结论

每个试点写接口只保留六块：基础信息、请求、响应（含典型错误）、前置条件与副作用、边界与失败行为、验收场景；状态/能力决策引用本文件，不在每个接口重复技术论证。通用鉴权/错误/时间规则在API§1只写一次。GET以后仅写权限、查询条件、结果边界和错误，不机械复制完整写接口模板。

本轮评估：格式能区分数据结构、业务结果与失败后状态，能暴露“超时不等于失败”“仅改统计不动余额”“跨起始日不是只改月份”等关键行为，适用于当前项目。无需全项目一口气改写；暂不生成整仓OpenAPI、SDK或新报告。D1–D3待用户选择属于显式决策，不能把候选分支当成已完成契约；选定后删去未选分支，不永久维护两套实现。

OpenAPI只严格承载已确认字段/组合、必填/默认、状态码、错误结构、鉴权与行为说明；资金副作用、重试超时、回滚与多动作一致性仍用场景验证。机器可读文档通过不代表业务实现正确。

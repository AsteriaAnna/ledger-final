## 3. 阶段 B：物理数据模型与最小工程骨架

任务：

1. 将逻辑实体映射为物理表/集合与字段。
2. 为用户归属、账户、交易、交易账户影响、资金变动、来源证据和预算定义主键、外键/关联约束、唯一约束及必要索引。
3. 明确金额整数分、日期时区、枚举、版本号与来源 ID 的持久化格式。
4. 建立可提交/回滚的 Unit of Work 或等价事务边界。
5. 建立服务端身份上下文、关系绑定的数据结构与资源归属检查。
6. 明确桌面端与 Android 端共用业务用例、API 契约和账务规则；平台差异留在客户端适配层。
7. 建立自动化测试入口与最小 CI；不先搭复杂部署流水线。

验收：

- 物理模型能映射逻辑数据模型的核心实体和关系。
- 当前用户 ID 来自已验证身份，不从请求体接受为授权依据。
- 账户余额和资金份额没有独立可写的第二份真相。
- 交易与资金变动能够原子提交/回滚。
- 双人只读权限在数据模型和服务端应用层中有明确承载，不留到 UI 完成后再补。

## 4. 阶段 C：第一个可运行垂直切片

目标：先做出一条真正可运行、可观察、可验收的路径，而不是先堆齐所有空模块。

包含：

1. 用户登录后的当前身份解析（采用阶段 A 选定的认证方案）。
2. 创建一个实际账户，设置起始日期、初始余额和资金份额。
3. 新建一笔普通支出或收入。
4. 查询交易详情、账户余额和资金份额。
5. 首页读取最小资金总览。
6. 发生校验失败时，保证数据未被部分写入。

验收场景：

- 创建初始余额 ¥5,000，初始份额合计必须恰好为 ¥5,000。
- 普通支出 ¥25.80 后，账户总额与资金份额都减少 ¥25.80，且份额扣减顺序正确。
- 普通收入 ¥10.00 后，自己的流动资金增加 ¥10.00。
- 把同一请求用同一个幂等键重试，不产生第二笔交易。
- 通过伪造他人 user ID 不能读取或修改未授权资源。
- 任何一次账务操作失败都不留下部分 Transaction 或 AccountFundMovement。

## 5. 阶段 D：交易生命周期与资金规则

按小任务依次完成：

1. 普通收入/支出及存款使用提醒。
2. 交易列表、搜索、筛选和详情。
3. 编辑交易字段与金额差额处理。
4. 删除交易及其账务影响。
5. 内部转账的双账户影响。
6. 真实退款与部分/多次退款（退款只由官方账单导入创建，手动记账不提供退款类型）。
7. 交易类型变更。
8. 历史交易、记账起始日期与余额影响状态。

验收：

- 每个任务均有成功、失败和重复提交测试。
- 转账两端影响金额相等、方向相反；不计收入或消费。
- 编辑交易只处理该交易，不自动重算后续交易；手动类型修改不得把普通交易改为 refund。
- 消费与退款独立删除；来源证据可供各自重新导入。
- 独立退款不检查原消费累计额度；资金份额必须与当前退款流入一致。
- 手动记账不能创建退款；官方退款无需原消费即可创建。
- 官方退款提取到账账户、实际金额、时间和类型；必要字段缺失明确待处理，退款不计普通收入。
- 退款按自身记账日期与账户起始日期判断余额影响；跨起始日期编辑需原子更新当前交易。
- 官方退款SourceRecord只关联独立refund Transaction；不建立消费关系。
- 起始日前的交易可查询和统计，但不影响该账户起始日后的余额。
- 任何失败都不留下单边转账、超额退款或份额不守恒状态。

退款验收：独立到账、部分/多次退款按各自来源去重、日期编辑、抵减开关、消费删除保留退款；本次脚本只验证字段与统计，正式账务仍待实现。

## 6. 阶段 E：首页统计与预算

任务：

1. 实现首页资金与四类资金份额汇总。
2. 实现本月花销、自然日平均、上月日均、日均变化率和本月预计花销。
3. 实现个人月度预算创建/修改、剩余额度和超支提示。
4. 实现绑定后对象资金可见的查询聚合，但不混入当前用户消费和预算。

验收：

- 所有资金金额由统一账务事实和资金份额汇总。
- 退款按自身记账日期月份及affects_spending修正统计与预算。
- 内部转账与信用还款不重复计为消费。
- 对象消费不占用当前用户预算。
- 超支时返回正数超支额；未超支时返回剩余预算。
- 使用固定日期和固定交易数据测试日均、变化率、预测结果，避免示例和实现出现算术矛盾。

## 7. 阶段 F：微信/支付宝官方账单导入

先用真实官方账单样例验证字段，不先增加 AI 识别层。

任务：

1. 自动识别固定格式的微信/支付宝文件；读取导出账户元数据、导出时间、起止范围、全量导出标记和声明记录数。
2. 校验表头、日期范围、声明行数与实际解析行数；不完整文件不执行缺失手动交易核对。
3. 用来源账户档案 + 官方交易单号建立稳定来源身份；商户订单号不作为唯一键。
4. 区分导出账户档案与行级支付渠道映射：前者标识哪个平台账号导出了文件，后者把零钱/银行卡/花呗/亲情卡映射到星账实际账户或信用来源。
5. 保存每次导入的 SourceObservation；重叠导出中同一交易状态变化时，按导出时间更新当前来源状态，不重复创建交易。
6. 将导入记录与手动交易、历史来源记录匹配；对确定的新交易调用统一交易用例，对已有交易只关联来源。
7. 识别退款实际到账账户、金额、时间与子类型，独立创建；不做原消费关联。
8. 对完整覆盖范围内未匹配的手动交易建立跨批次唯一 ImportReconciliationItem，提供“删除这笔手动账单”或“保留并标记已核对”。
9. 重叠导入复用既有核对项，仅新建项在本次结果中提示；后续匹配到官方来源时自动结案。
10. 汇总新增、关联、重复、核对项新建/复查和失败数量。

验收：

- 同一文件/同一幂等请求重复导入不重复入账。
- 已存在的同一笔手动交易可关联官方来源，不重复创建。
- 不稳定 ID 场景不只凭金额、日期、商户相同就静默合并。
- 官方退款无需原消费；必要字段、到账账户不明时展示具体原因，禁止当普通收入掩盖。
- 手动修正的重要字段不会被官方导入静默覆盖。
- 手动交易未找到来源时只在覆盖范围完整、来源档案及支付渠道映射明确的前提下生成核对项；用户可删除交易或保留并标记已核对，系统不自动删除。
- 每种受支持交易状态都有明确处理结果。
- 使用真实微信、支付宝文件做逐行对照，记录新增、关联、跳过、来源待处理、未匹配手动交易核对项的准确数量。
- 对覆盖范围不明确或来源档案/支付渠道映射不确定的批次，不生成“官方来源未找到”的核对项。
- 同一来源档案与手动交易最多一个核对项；重叠导入不重复新建/提示，后续来源匹配则自动结案。

## 8. 阶段 G：双人绑定与对象只读查看（首发必需）

双人支持是首发核心范围，不是可选的远期增强。本阶段安排在账务核心可运行之后实施，但数据归属、关系模型和服务端权限检查必须从阶段 B 开始就存在；首发版本不能在未完成本阶段的情况下宣称达到完整产品验收。

本阶段交付用户可见的绑定流程，并让桌面端与 Android 端共用同一套服务端业务规则和数据。

任务：

1. 按阶段 A1 确认的凭据机制完成绑定。
2. 首页同屏展示双方四类资金。
3. 账户与账单提供查看对象数据的入口。
4. 对象的账户和交易仅只读；写接口必须由服务端拒绝。
5. 双方预算保持独立，不自动合并账单或虚构共同账户。

验收：

- 未绑定用户不能通过传入对方 ID 查看数据。
- 绑定后可以读取对象允许开放的账户/账单。
- 绑定后仍不能创建、编辑或删除对象数据。
- 双方资金份额按归属人与性质显示，不因保管关系混淆。
- 当前用户预算不包含对象消费。

- 检查错误反馈、加载/失败状态和重复提交体验。
- 确认 CI、构建、部署与最基本的运行说明。
- 更新 README、路线图与验收记录，只把真实运行通过的功能标记为完成。

## 10. AI 开发任务模板

每次只给一个可独立验收的小任务，并包含：

1. **目标：** 用户可观察到的变化或明确的底层约束。
2. **依据：** 相关业务规则、数据模型、API 和模块边界章节。
3. **允许修改范围：** 需要修改的模块和明确禁止触碰的区域。
4. **前置条件：** 依赖接口、未决规则和测试数据。
5. **验收标准：** 至少一个正常场景、一个失败场景；账务写操作还要验证原子性/幂等性。
6. **交付结果：** 修改文件、运行过的测试、未解决的问题与下一步。

不接受只说“实现完了”但没有修改清单、测试结果和已知限制的交付。

# P0-T01｜建立执行与Git规则

所属计划：[P0交付与上下游](../PHASE_DELIVERIES_AND_DEPENDENCIES.md#p0)。本卡交付P0-D1，供P0-T02、P0-T03及后续任务使用。状态仅维护在[实施计划§2.6](../IMPLEMENTATION_PLAN.md#26-阶段控制与当前进度)。

## 固定执行约束

只执行本卡编号步骤、指定读取和允许改动路径。先核对输入与基线，再逐步操作和验证。遇到输入缺失、文档冲突、版本偏离、命令/测试失败或需要范围外改动，立即暂停，保留现场并汇报“当前步骤、已完成项、文件/提交、已运行检查及实际结果、阻塞事实、需要用户提供或决定的事项”。暂停后等待用户补充指令或修订任务卡；不自行选择修复方案、替代技术、扩展任务或反复重试。完成本卡即交接，下一张卡由用户另行启动。

## 允许改动

- 新建根目录`AGENTS.md`。
- 修改`README.md`的AI任务入口与Git操作说明。
- 更新`docs/IMPLEMENTATION_PLAN.md`的§2.6中P0-T01这一行。

## 操作步骤

1. 在仓库根目录执行下列命令，记录分支、HEAD与工作区状态。已有未提交变动时按固定执行约束暂停；工作区干净后，从指定基线建立本卡工作分支`docs/p0-t01-<短提交号>`，重名时暂停报告已有分支。

   ```bash
   git status --short --branch
   git branch --show-current
   git rev-parse HEAD
   git diff --name-only
   ```

2. 创建简短`AGENTS.md`，按以下六项写实际可执行的规则：
   - 先读用户指定任务卡，再读卡中指定文件/章节；使用`rg -n`定位章节，按范围读取。
   - 一次执行一张卡；卡内给出的输入、步骤、修改路径和验证项共同限定操作范围。
   - 将本卡“固定执行约束”的暂停及汇报行为作为仓库通用执行规则；卡内协议保留，供独立对话直接读取。
   - 开工记录分支/HEAD/工作区；按显式文件路径暂存，只提交本卡变动；提交格式使用`docs: ...`等Conventional Commits。
   - 个人原始账单、凭据、日志明细和备份存私有位置；代码与文档只记录配置名称和脱敏结果。
   - 测试结果分别标明文档、参考模型、真实HTTP/数据库、真实云端四种证据；任务完成汇报产物提交、验证结果和未满足输入，然后停在本卡。

3. 在README增加一个简短AI入口，链接阶段交付文档、当前任务状态和本卡。给出读取顺序“用户指定卡→输入表→操作→验证→交接”。将Git说明改为可操作的“从指定基线建立任务分支、按路径暂存、检查差异、提交产物、记录验收”；远端推送及合并按用户对当前任务的明确授权执行。

4. 执行下面的验证表。全部通过后，只暂存`AGENTS.md`与`README.md`，提交`docs: establish P0 execution baseline`，取得产物提交SHA。在实施计划P0-T01行写入“已验收、该SHA、实际通过的检查摘要”，单独提交`docs: record P0-T01 acceptance`。Git命令失败时保留现场并暂停。

## 验证与测试

| 检查 | 具体执行 | 通过标准 |
|---|---|---|
| 修改范围 | 对比开工SHA运行`git diff --name-only <开工SHA>` | 仅出现本卡允许的三个文件 |
| 内容与入口 | 逐条核对步骤2六项；从README打开三个相对链接 | 六项完整，链接指向实际文件和章节 |
| 暂停行为走查 | 将“指定资料缺失”“检查命令失败”“用户要求以外的技术选择”代入AGENTS和本卡 | 三种情形均走暂停→事实汇报→等待用户的路径 |
| 格式及提交 | `git diff --check`；暂存后`git diff --cached --name-only`和`git diff --cached --check` | 无空白错误；暂存文件与当前提交用途一致 |
| 交付可定位 | `git show <产物SHA>:AGENTS.md`；检查验收记录 | 上游规则可从确定提交读取，工作区最终干净 |

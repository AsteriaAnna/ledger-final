所属计划：[P0交付与上下游](../PHASE_DELIVERIES_AND_DEPENDENCIES.md#p0)。上游是[P0-T01](P0-T01_EXECUTION_BASELINE.md)、[P0-T02](P0-T02_DOCUMENT_ROUTING.md)、[P0-T03](P0-T03_P1_INPUTS.md)的验收记录与产物提交。本卡交付P0-D4。

## 固定执行约束

只执行本卡编号步骤、指定读取和允许改动路径。先核对输入与基线，再逐步操作和验证。遇到输入缺失、文档冲突、版本偏离、命令/测试失败或需要范围外改动，立即暂停，保留现场并汇报“当前步骤、已完成项、文件/提交、已运行检查及实际结果、阻塞事实、需要用户提供或决定的事项”。暂停后等待用户补充指令或修订任务卡；不自行选择修复方案、替代技术、扩展任务或反复重试。完成本卡即交接，下一张卡由用户另行启动。

## 操作步骤

1. 在P0-T03验收记录提交上核对干净工作区，建立`docs/p0-t04-<短提交号>`分支，记录本卡开工SHA。用`git merge-base --is-ancestor <上游产物SHA> HEAD`逐个确认三张卡产物在当前历史中；记录每项退出码。

2. 依验证表检查P0-D1–D3。对所有文件路径区分“已交付文件”和“未来阶段计划位置”：所有当前Markdown链接必须能打开；未来工程路径作为计划文字登记，不按缺文件判失败。

3. 从本卡起点反查P0的修改清单，确认业务规则、逻辑模型、产品功能、机器契约、参考实验保持基线内容；API/字段正文改动仅为P0-T02指定搬移和等价链接调整。每条重复技术正文的删除均有实施计划§7对应位置。

4. 全部检查通过后，在实施计划§2.6把P0阶段改为“已验收”；P0-T04行记录本卡检查所针对的开工SHA、实际命令/结果摘要。下一步写“用户启动P1首卡编写，领取实施计划§8和P1-D1的最小RPC验证；外部未提供项在首次使用前领取”。保留I01–I08尚待用户提供项的真实状态。

5. 运行`git diff --check`，仅暂存实施计划，检查暂存差异后提交`docs: accept P0 and hand off P1 inputs`。报告交接提交SHA和P1输入入口，结束本卡。

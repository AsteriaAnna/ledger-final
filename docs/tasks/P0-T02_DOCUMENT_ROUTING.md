# P0-T02｜整理文档职责与模块读取入口

所属计划：[P0交付与上下游](../PHASE_DELIVERIES_AND_DEPENDENCIES.md#p0)。上游是[P0-T01](P0-T01_EXECUTION_BASELINE.md)的P0-D1，本卡交付P0-D2，供P0-T03/P0-T04及后续任务卡使用。状态仅维护在[实施计划§2.6](../IMPLEMENTATION_PLAN.md#26-阶段控制与当前进度)。

## 固定执行约束

只执行本卡编号步骤、指定读取和允许改动路径。先核对输入与基线，再逐步操作和验证。遇到输入缺失、文档冲突、版本偏离、命令/测试失败或需要范围外改动，立即暂停，保留现场并汇报“当前步骤、已完成项、文件/提交、已运行检查及实际结果、阻塞事实、需要用户提供或决定的事项”。暂停后等待用户补充指令或修订任务卡；不自行选择修复方案、替代技术、扩展任务或反复重试。完成本卡即交接，下一张卡由用户另行启动。

1. 核对上游验收记录和干净工作区，从上游验收记录提交建立`docs/p0-t02-<短提交号>`分支。记录开工SHA，并在仓库外保存本次将搬移的原文块、各块来源章节、OpenAPI哈希和24个operationId列表，供前后比较。

2. 按以下固定映射搬移API正文，逐段保留句子、参数表和例子；只调整标题层级及相对链接。每个新文件开头标明其维护职责和返回API索引的链接。

   | 原API章节 | 正文唯一新位置 |
   |---|---|
   | §1通用行为、§3共用字段与完整实例 | `docs/api/COMMON.md`，保持两个章节 |
   | §4 M1接口行为 | `docs/api/M1_IDENTITY.md` |
   | §5 M2接口行为 | `docs/api/M2_ACCOUNTS.md` |
   | §6 M3接口行为 | `docs/api/M3_TRANSACTIONS.md` |
   | §7 M4接口行为 | `docs/api/M4_IMPORTS.md` |
   | §8 M5接口行为 | `docs/api/M5_OVERVIEW.md` |

   `API_CONTRACT.md`保留原文件路径、§1–9标题及其锚点；§2保留24操作索引，§9保留边界摘要；搬走的章节只写正文链接。原operation标题也保留为链接占位，保持已有操作锚点可达。这样旧模块/操作链接仍能到达对应正文。新文件中的OpenAPI相对链接指向`../../openapi.yaml`。

3. 将模块边界§3–7按原顺序逐字搬到`docs/import/OFFICIAL_FIELDS.md`，保留字段表、规则和真实样本事实；调整相对链接。原文件保留§3–7标题及微信/支付宝字段子标题，各节正文替换为新文件对应章节链接，保持原锚点可达。§1–2和§8继续负责模块协作与提交边界。

4. 将模块边界§9收敛为三个明确关系：M2/M3/M4各自交付计划；应用用例经同一持久化适配器一次提交；SQL函数/授权由有序迁移维护。具体RPC步骤、并发/权限防护与恢复方案直接链接实施计划§7.3、§7.5–7.6。删除前逐句核对这些技术细节已在被链接小节中表达；任何找不到对应依据的句子先保留并按协议暂停汇报。

5. 在README六份核心入口表后增加“模块读取入口”表。各行分别为通用接口、M1、M2、M3、M4、M5；每行链接本模块业务规则章节、API独立文件及相关模型/边界章节。M4额外直达`OFFICIAL_FIELDS.md`；技术任务直达实施计划§7的具体章节。表中只写资料位置和读取用途。

6. 完成验证表后，按明确文件路径暂存步骤2–5产物，提交`docs: route API and import knowledge by module`。把产物SHA和实际检查摘要写入P0-T02行，提交`docs: record P0-T02 acceptance`。将临时比较材料留在仓库外。

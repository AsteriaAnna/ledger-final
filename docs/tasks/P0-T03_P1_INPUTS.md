# P0-T03｜明确P1开工输入与隔离约定

所属计划：[P0交付与上下游](../PHASE_DELIVERIES_AND_DEPENDENCIES.md#p0)。上游是[P0-T02](P0-T02_DOCUMENT_ROUTING.md)交付的稳定资料入口，本卡交付P0-D3，供P0-T04和P1任务卡编写者使用。状态仅维护在[实施计划§2.6](../IMPLEMENTATION_PLAN.md#26-阶段控制与当前进度)。

## 固定执行约束

只执行本卡编号步骤、指定读取和允许改动路径。先核对输入与基线，再逐步操作和验证。遇到输入缺失、文档冲突、版本偏离、命令/测试失败或需要范围外改动，立即暂停，保留现场并汇报“当前步骤、已完成项、文件/提交、已运行检查及实际结果、阻塞事实、需要用户提供或决定的事项”。暂停后等待用户补充指令或修订任务卡；不自行选择修复方案、替代技术、扩展任务或反复重试。完成本卡即交接，下一张卡由用户另行启动。

## 输入与读取

| 输入 | 精确位置 | 读取目的 |
|---|---|---|
| 执行及资料基线 | P0-T02验收记录提交、AGENTS、README的技术资料入口 | 取得确定版本及已有引用方式 |
| P1交付和依赖 | 阶段交付文档§2、P1 | 覆盖D03–D09以及P1-D1–D3所需输入 |
| 已定技术与验证 | 实施计划§7.1–7.8 | 从既定路线导出资源需求、隔离边界及验证预期 |
| 账务/来源提交约束 | 模块边界§1–2、§8–9；逻辑模型§4–5、§8 | 确定最小试验需观察的记录和并发条件 |
| 已给定环境事实 | 仓库内已有的非敏感事实，或本次用户随任务提供的材料 | 只填写能指向来源的实值；其余外部值登记为P1领取项 |

本卡编写P1输入约定，不执行云端验证。完整填写“需要什么、由谁给、何时必须有、如何验证可用”就是本卡操作；外部实值尚未提供时准确标记领取关卡，P1领取该输入时再按卡检查。

## 允许改动

- `docs/IMPLEMENTATION_PLAN.md`新增§8“P1开工输入登记”。
- 同文件§2.6中P0-T03这一行。

## 操作步骤

1. 核对上游验收与工作区，从P0-T02验收记录提交建立`docs/p0-t03-<短提交号>`分支，记录开工SHA。

2. 在实施计划§8建立一张输入登记表，列为“输入ID、所需值/证据、提供者、当前已知值及来源、P1首次使用动作、可用性检查”。按以下项目逐行填写。

   | 输入ID | 必须登记的内容 | P1领取时执行的检查 |
   |---|---|---|
   | I01 | 本地运行系统、Node版本/可执行路径、SQL/HTTP调用工具 | 打印版本，运行一个受控只读请求并记录响应 |
   | I02 | 隔离CloudBase环境名称/ID/地域/用途、共享PG访问路径、批准使用的库/数据范围 | 从用户给定资源证据核对环境；读取允许的元数据，确认请求落到隔离目标 |
   | I03 | 建表/函数/授权操作身份与后端受限调用身份，凭据安全注入位置 | 分别验证允许操作；普通客户端调用内部写RPC应被拒绝 |
   | I04 | 两个测试Auth身份、认证主体与内部User映射方式、测试客户端来源 | 后端验证有效、无效、过期身份；准备跨用户访问用例 |
   | I05 | 最小云托管/Web托管入口、调用来源、配置项名称和日志读取权限 | 检查Web→Node→共享PG的实际路径，记录配置归属 |
   | I06 | 与被测数据隔离的恢复目标、私有导出位置、加密/访问方式 | 检查导出和恢复角色权限；恢复后可比对原试验数据 |
   | I07 | 创建/使用资源的授权范围、费用观察入口、由用户确定的开销边界 | 将拟用操作与授权对应，记录实际用量读取方式 |
   | I08 | 合成账户/交易/来源/幂等状态的固定输入、金额单位、时钟和独立预期 | 检查样本身份、金额与预期互相一致；可重复初始化和清理试验数据 |

   对源材料没有给出的环境ID、域名、身份和价格写“待用户提供；阻塞对应P1动作”，保留具体提供者和检查方法。P1通过检查后再回填真实值与证据。本卡不把未知值填写为已有能力。

3. 在§8添加一张最小验证领取表，把P1-D1–D3与输入ID相连：原子提交/回滚领取I01–I03/I07/I08；权限与最小部署领取I02–I05/I07；导出恢复领取I02/I03/I06–I08。每行写执行前必须满足的输入以及将写入的隔离对象；测试预期直接链接§7.8或§7.6，不复制算例。

4. 在§8用Mermaid画资源关系：测试浏览器→测试Auth；浏览器→测试Node；Node→受限RPC→隔离PG；隔离PG→私有导出→独立恢复目标。将建表/授权身份与Node受限身份画成不同节点，标明使用位置。

5. 写明P1首卡编写者的领取顺序：先确认I02/I03/I06/I07的资源与授权，再确定I01的执行命令，接着把I08的最小输入和§7.8第一项验证落到允许的SQL/Node文件及精确命令；真实Auth/部署验证领取I04/I05。若资源条件缺失，P1首卡在对应动作前暂停汇报。

6. 完成验证表后，只暂存实施计划§8的新增内容，提交`docs: define P1 execution inputs`。将产物SHA与实际检查摘要写入P0-T03行，提交`docs: record P0-T03 acceptance`。

## 验证与测试

| 检查 | 具体执行 | 通过标准 |
|---|---|---|
| 输入覆盖 | 将P1-D1、D2、D3逐项映射到I01–I08 | 每项产物都能找到运行、数据、权限、资源及验证输入；每个输入有提供者 |
| 已知/未知分开 | 对每一个实值打开其来源；对每一个待提供项检查阻塞动作 | 没有从环境名猜权限、从套餐猜可恢复性或从参考脚本猜云端完成情况 |
| 隔离走查 | 沿Mermaid逐个检查测试、后端、管理、导出和恢复角色 | 写入目标是明确的隔离数据；恢复目标与源试验数据隔离；凭据只出现名称和安全存放方式 |
| 领取场景 | 假设I03缺失，沿最小验证表检查执行顺序 | P1在第一个需要该权限的动作前暂停；能汇报缺失项和用户提供者 |
| 内容唯一性 | 对比§8和§7.3/§7.6/§7.8 | §8只维护实际输入/领取关系；技术选择、算法与算例仍在原位置 |
| 差异检查 | `git diff --check`和`git diff <开工SHA> -- docs/IMPLEMENTATION_PLAN.md` | 只新增§8并更新本卡状态行；原技术与业务条款保持一致 |

## 交接

向用户报告P0-D3产物SHA、验收记录SHA、P1输入登记入口、已知事实和仍待提供的资源ID清单。P0-T04接收本卡结果；P1卡编写者据此填精确命令与可写对象，再由用户启动实际验证任务。

# 星账｜工程模块边界

**版本：** v0.1  
**阶段：** 工程边界设计稿  
**状态：** 候选方案，待审阅  
**业务基线：** BUSINESS_RULES_DISCUSSION.md v2.5  
**数据基线：** LOGICAL_DATA_MODEL.md v0.2  
**接口基线：** API_CONTRACT.md v0.1

本文定义实现阶段的职责边界、依赖方向和写入权限。它是逻辑工程设计，不要求立即创建对应目录或类，也不代表软件已经实现。

## 1. 设计目标

1. 将 M1–M5 业务职责映射到可维护的工程模块。
2. 确保手动记账、交易编辑、退款、转账和官方导入最终使用同一套账务规则。
3. 防止前端、导入解析器或统计代码绕过统一账务入口直接修改余额。
4. 让 AI 可以按一个清晰的模块契约完成小任务，而不是每次修改都扫描或重构整个项目。
5. 先采用模块化单体；当前没有将模块拆成独立服务的需求。
6. 首发必须具备可用的移动端记账体验；桌面端与 Android 端共享业务能力、API 契约和数据规则，差异主要位于客户端适配层。
7. 双人数据归属、关系绑定与服务端只读权限从第一天纳入架构，不作为后期补丁。

## 2. 推荐分层

~~~mermaid

    API --> APP["应用用例层"]

    APP --> ACCOUNT["M2 账户与资金管理"]
    APP --> LEDGER["M3 交易账务"]
    APP --> IMPORT["M4 官方导入与来源证据"]
    APP --> STATS["M5 统计与预算"]
    LEDGER --> RULES["共享账务规则"]
    ACCOUNT --> RULES
    IMPORT --> PARSER["解析、标准化与匹配"]
    IMPORT --> LEDGER
    IAM --> PORTS["Repository / Unit of Work 接口"]
    ACCOUNT --> PORTS
    LEDGER --> PORTS
    IMPORT --> PORTS
    STATS --> PORTS
    PORTS --> STORE["持久化实现"]
~~~

分层说明：

- **API 适配层：** 把 HTTP 请求转换为应用命令/查询，并把结果转换为统一响应。
- **应用用例层：** 组织一次完整用户操作，执行身份与资源权限检查，并协调需要原子提交的模块。
- **业务模块：** 负责对应的领域概念和业务行为，不依赖 HTTP、页面框架或具体数据库 SDK。
- **共享账务规则：** 只计算、验证并返回结果计划，不自行读取或写入数据库。
- **持久化接口：** 为业务用例提供读取、写入和事务边界；具体数据库和 ORM 由技术选型决定。

这不是微服务架构。首期可将这些边界实现为同一后端进程中的模块和应用服务。

## 3. 模块职责与输入/输出

| 模块 | 负责的事情 | 主要输入 | 主要输出 | 不允许承担的职责 |
|---|---|---|---|---|
| M1 身份、关系与权限 | 解析当前登录用户；查询绑定状态；校验自己/对象数据的读写权限 | 已验证身份、资源归属、绑定关系 | 当前用户上下文、允许的操作范围、权限结果 | 不直接创建交易、资金变动或替其他用户写账 |
| M2 账户与资金管理 | 创建/编辑账户；设置初始余额与起始日期；手动调整账户内资金归属/性质；查询账户及资金份额 | 账户基本信息、初始资金分配、资金调整命令 | 账户信息、计算后的余额/资金份额、校验错误 | 不提供任意余额覆盖；不处理交易专属扣款顺序；不删除账户 |
| M3 交易账务 | 创建、编辑、删除交易；处理收入、支出、转账、退款；维护交易账户影响与交易生成的资金变动 | 已验证的交易命令、账户状态、当前交易版本 | 交易结果、账户影响、资金变动计划、存款提醒 | 不解析 Excel/CSV；不直接处理 HTTP；不自行计算首页统计 |
| 共享账务规则 | 计算支出分配、金额差额、退款逆序恢复、转账校验、账户起始日期影响状态和统计分类 | 交易事实、账户资金份额、来源/退款关联、日期 | 可验证的计算结果或明确的业务错误 | 不访问数据库、网络、文件、AI 模型或系统时间 API；不直接提交写入 |
| M4 官方导入与来源证据 | 解析微信/支付宝官方文件；标准化字段；管理导入批次、来源观察、来源身份和账户映射；识别重复/歧义 | 官方账单文件、平台、当前用户、已保存映射和来源记录 | 标准化记录、匹配建议、导入结果摘要、待处理项 | 不直接写余额或 AccountFundMovement；不另造一套交易规则；不静默合并不确定的记录 |
| M5 统计与预算 | 读取资金总览；计算个人消费、日均、预测、变化率；查询/修改个人月度预算 | 交易事实、退款关系、资金变动、月份、当前用户 | 首页总览、筛选统计、预算与超支结果 | 不写交易账务；不把对象消费混入当前用户预算；不维护第二套余额真相 |
| API 适配层 | 路由、格式校验、身份上下文接入、DTO 转换、HTTP 状态与错误码映射 | HTTP 请求、登录凭据、应用服务结果 | JSON 响应、统一错误响应 | 不决定资金扣减顺序、退款归属月份或来源匹配结论 |
| 持久化与 Unit of Work | 实现 Repository、事务提交/回滚、并发版本检查和必要的唯一约束 | 应用用例发起的读写请求 | 已提交的持久化结果或冲突 | 不把产品规则藏进数据库适配层；不允许业务模块绕过应用用例随意写表 |

## 4. M1–M5 与产品区域的对应关系

| 业务模块 | 对应产品区域 | 主要责任 |
|---|---|---|
| M1 身份、关系与权限 | 我的；账户/账单中的访问权限 | 当前身份、关系绑定、对象只读查看 |
| M2 账户与资金管理 | 账户 | 实际账户、起始余额、资金归属与性质 |
| M3 交易账务 | 账单、手动记账 | 交易事实、编辑删除、转账、退款、资金影响 |
| M4 官方导入与来源证据 | 记账与导入 | 官方文件、去重、来源映射、导入结果 |
| M5 统计与预算 | 首页总览、预算设置 | 资金汇总、消费指标、个人预算 |

共享账务规则、API 适配层和持久化层是横向支撑，不是新增的用户可见产品模块。

## 5. 账务写入边界

### 5.1 谁可以生成资金变动

AccountFundMovement 是统一的资金变动事实，但不同业务命令只允许生成自己负责的原因：

- **账户用例：** 创建初始资金变动、修正账户初始状态、执行账户内手动资金重新分配。
- **交易用例：** 根据收入、支出、转账、退款、交易金额/类型修改和删除生成或撤销对应的交易资金影响。
- **官方导入用例：** 只负责来源证据和匹配；新交易必须调用交易用例，不得自行创建资金变动。
- **统计/预算用例：** 只读，不创建资金变动。
- **API/前端：** 不直接写入资金变动，也不直接覆盖账户余额。

所有这些写入必须经过应用用例并使用统一的持久化事务边界。不能把“同一操作需要原子提交”的规则拆散到多个无法一起回滚的请求中。

### 5.2 交易处理的唯一入口

手动记账、官方账单确认创建、编辑、类型变更、退款和转账，必须调用同一套交易应用用例与共享账务规则。

官方导入不能复制一份支出扣减算法；编辑交易也不能用前端重新计算资金份额；删除交易不能只删 Transaction 而留下仍在余额中生效的资金变动。

### 5.3 余额与统计的唯一来源

- 当前账户余额由有效 AccountFundMovement 汇总。
- 账户内资金份额由账户、归属人和资金性质对应的有效 AccountFundMovement 汇总。
- 消费统计根据 Transaction 的类型、账务语义、交易日期与退款关系计算。
- 个人预算按当前用户独立计算。
- 首页和账户页不能分别保存可独立修改的余额副本。

## 6. 模块依赖规则

1. API 适配层只能调用应用用例，不直接访问 Repository。
2. 共享账务规则保持确定性、可独立测试；输入相同，输出应相同。
3. 业务模块不依赖具体数据库、HTTP 框架、前端组件或云厂商 SDK。
4. 官方导入依赖解析/标准化/匹配能力，并通过交易应用用例创建交易；不能反向把导入依赖塞进交易核心。
5. 统计模块可读取交易和资金变动数据，但不能写入交易账务。
6. 关系与权限检查必须发生在服务端应用用例；隐藏前端按钮不能替代授权。
7. 不允许循环依赖。两个模块确需协作时，通过明确的应用用例或接口完成。
8. 首期不拆微服务、不为每个实体单独建一个模块，也不为了“架构完整”提前建设事件总线、插件系统或复杂工作流。

## 7. 原子操作与跨模块协作

以下业务操作必须在同一事务边界内完成：

- 创建/编辑交易及其账户影响、资金变动。
- 转账的两端账户影响与对应资金变动。
- 创建/编辑退款、校验原消费累计退款额、恢复资金份额。
- 删除消费、删除其关联退款、解除相关来源记录的当前关联。
- 官方导入确认新交易、写入交易账务、关联 SourceRecord 并更新批次结果。
- 修改账户初始状态、初始资金份额和受影响账户交易的有效/历史状态。

如果某项操作不能安全地在一个事务中完成，必须先定义明确的处理中状态与恢复策略；当前契约不允许先返回成功、后台再补写账务。

## 8. 外部能力的边界

- 首发必须保证移动端的账户选择、手动记账、账单查看和结果反馈可用；具体客户端形式由 D1 决策确定。
- 桌面端与 Android 端共享同一套业务用例、API 契约和账务规则；不得复制出两套记账算法。
- 双人绑定和对象只读查看属于首发范围；数据归属与服务端授权必须从最小垂直切片开始实现。
- 首期官方账单导入优先使用微信/支付宝文件中的确定性字段和规则。
- AI/视觉模型不进入普通手动记账或账务规则核心，也不用于重新猜测官方文件中已明确的字段。
- 截图识别在产品功能地图中明确暂缓；移动端首发体验不依赖截图识别。
- 登录供应商、数据库、部署方式和前端框架仍待技术选型；业务模块不应提前绑定某一厂商 SDK。

## 9. 实现前需明确的边界问题

这些问题不要求重新讨论全部业务规则，但相关功能实现前必须有明确答案：

1. **退款到账账户不同于原消费账户：** 逻辑模型要求分别记录两个账户，但需确认退款恢复的资金归属/性质如何记入实际到账账户。
2. **原消费是信用消费：** 该交易没有现金账户扣减份额，现有规则未完整定义后续退款的资金份额恢复方式。
3. **修改账户记账起始日期：** 需要明确如何原子重建该账户受影响交易的 applied / historical_only 状态与资金变动。
4. **关系绑定凭据：** 绑定 token 的生成、过期、验证和防止被重复使用的方式待认证/交互方案确定。
5. **官方文件匹配：** 稳定外部 ID、来源账户字段、交易状态、退款关联字段必须用真实微信/支付宝文件验证。

这些问题只阻塞各自相关实现，不应成为继续完成无关基础模块的理由。

## 10. 模块边界验收标准

工程骨架准备完成后，应能验证：

- 每个应用用例都有明确的输入、输出、权限检查和失败结果。
- 任意交易写入路径都经过统一账务规则。
- 导入解析器没有直接写账户余额或资金变动的代码路径。
- 首页统计与账户余额没有独立的可写副本。
- 绑定对象的写请求在服务端被拒绝。
- 账务事务失败时没有留下半笔交易、单边转账或未匹配资金变动。
- 资金扣减、退款恢复、金额编辑与删除的关键规则可用纯逻辑测试验证。
- 业务规则、逻辑数据模型、API 契约和模块边界之间没有相互矛盾的重复定义。

**说明：** 本文件定义建议的模块责任，不指定最终目录结构或技术栈。物理模块和文件拆分应以首个可运行的垂直切片为准，避免过早建立大量空目录。

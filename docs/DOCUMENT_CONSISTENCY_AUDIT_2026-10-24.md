**审查基线：** AsteriaAnna/ledger-final 的 main 分支  
**审查范围：** README、产品功能地图、冻结业务规则、逻辑数据模型、API 契约、工程模块边界、实施计划、路线图

**来源边界：** 本审查只以当前 ledger-final 仓库文档为基线，不把其他旧仓库的实现或复现结果当作本项目现状，也不冻结具体退款识别算法。

## 1. 当前进度判断

星账仍处于**产品规则已冻结、逻辑模型/API/工程边界候选稿持续收敛、尚未进入可运行产品实现**的阶段。

本轮已冻结并同步的产品行为：

1. 手动记账只提供收入、支出和转账，不提供用户手动新建退款的入口。
2. 退款仍是正式账务类型，但只能由官方账单导入流程依据官方退款来源创建，并且必须关联原消费；不能把退款当作普通收入。
3. 如果官方退款来源暂时无法确认原消费，不得静默丢弃、不得作为普通收入入账，也不得伪装成已完成的退款交易；来源记录保留待处理。
4. 官方账单导入完成后，对本次**可确认完整的覆盖范围**内、来源平台和账户映射相符、按现有交易信息应当出现在该文件中的手动交易进行集中核对。
5. 若未找到对应官方来源，生成待确认提示。该提示不代表系统已判定原交易错误；用户确认后原交易保持不变，发现录入错误时再使用现有账单编辑/删除流程。
6. 覆盖范围不明确或来源账户映射不明确时，不判定手动交易“未出现在官方账单”。导入核对不自动删除、覆盖或改写交易，也不阻断其他成功导入记录。

这些是产品行为，不是具体匹配算法。订单号、外部 ID、字段解析和候选排序仍须在真实文件验证阶段确定。

## 3. 一致性检查结果

### 3.1 已修正的冲突

| 冲突 | 原因 | 统一结果 |
|---|---|---|
| 产品手动录入只列收入、支出、转账，但 API 曾允许 POST /transactions 创建退款 | 输入渠道规则没有贯穿到 API | 手动创建只允许收入、支出、转账；退款仍作为领域类型，由官方导入流程创建 |
| “退款关联原消费”与“官方退款来源关联交易”容易被当成同一关系 | 两者的目标对象不同 | SourceRecord → refund Transaction 表示来源归属；refund Transaction → original expense 表示退款父子关系 |
| “官方来源行找不到已有交易”与“账本中有手动交易但官方文件没找到对应行”混为一类 | 两种情况的证据方向相反，处理方式不同 | 前者用 SourceRecord 待处理状态；后者用 ImportReconciliationItem |
| 导入后未匹配可能被误解为系统自动判错 | 文件覆盖范围或来源账户可能不完整/不明确 | 只有覆盖范围可确认完整、来源平台和账户映射明确时才生成核对项；不自动删改原交易 |
| 退款可能被错误地按普通收入入账 | 无法关联原消费时缺少安全边界 | 无法确认原消费的官方退款来源保持待处理，不作为普通收入或已完成退款入账 |
| 路线图、实施计划可能继续引用旧版本号 | 下游文档分别更新 | 版本基线统一到业务 v2.6、产品功能地图 v0.2、逻辑模型 v0.3、API 契约 v0.2、工程边界 v0.2、实施计划 v0.2 |

### 3.2 数据模型是否需要新实体？

需要一个轻量的核对状态概念。ImportReconciliationItem 记录“某次导入覆盖范围内有一笔手动交易未找到对应官方来源”及其确认状态。

这不是新增异常管理中心，也不是账务事实：

- 它不创建交易，不改变账户余额或资金份额。
- 它不替代 SourceRecord，因为官方文件里没有对应来源行。
- 用户确认只更新核对状态；若要改交易，仍走现有编辑/删除操作。
- 具体物理字段、唯一约束和跨批次提醒抑制仍需在物理 Schema 前审阅。

### 3.3 API 契约是否完整？

API v0.2 已表达两类导入结果和用户确认未匹配手动交易的候选操作，但**还不是最终定稿**。仍需补齐：

1. 官方退款来源无法唯一找到原消费时的独立解析动作。不能使用普通 link_existing_transaction 把退款来源直接连到原消费。
2. 核对项的确认状态如何持久化，以及相同/重叠覆盖范围的重复提示策略。
3. coverage.complete 如何根据实际官方文件元数据或用户确认的导出范围得到；若无法证明覆盖完整，应跳过“未找到来源”判断。
4. 对官方来源稳定外部 ID、来源账户和导入范围的验证结果，应在最终唯一约束与接口行为冻结前记录。

## 4. 未完成事项分类与适当解决时机

### A. 物理 Schema 前必须收敛

| 事项 | 影响范围 | 为什么此时要处理 |
|---|---|---|
| 退款到账账户不同于原消费账户时，如何恢复资金份额 | 退款账务、账户影响、资金变动、API | 关系和账户效果必须能表达真实到账账户；不能等退款代码写完再补 |
| 原消费是信用消费、没有现金扣减份额时，退款如何分配 | 退款账务、统计、资金变动 | 现有逆序恢复规则没有可直接恢复的现金份额 |
| ImportReconciliationItem 的持久化状态、唯一性和生命周期 | 逻辑模型、物理 Schema、导入 API | 用户确认必须可保存；编辑/删除原交易后不能留下悬空核对项 |
| 官方来源稳定 ID、来源账户和导入范围字段 | SourceRecord、去重索引、导入幂等 | 唯一约束不能在未验证来源字段的情况下凭空确定 |

这些事项会影响数据结构或账务不变量。可以继续无关模块的方案准备，但不应冻结相关物理 Schema。

## 5. 对技术选型、存储和认证的影响

### 技术选型

新增退款与导入后核对规则**不要求改变客户端、前端框架、后端运行环境或数据库供应商**。它们只要求选定的方案能提供：

- 可靠的原子事务；
- 对来源记录和账务交易的唯一性/引用完整性控制；
- 可持久化的导入批次与核对确认状态；
- 服务端执行的用户数据归属和只读权限检查。

具体技术选型仍按 D1/D2/D4 的独立决策顺序处理，不因为本次规则而预先锁定技术。

### 数据存储

这次规则确实影响逻辑模型：需要保存核对项及确认状态；同时必须区分来源记录与退款父子关系。它不要求另建退款服务或复杂异常系统。退款到账账户不同、信用消费退款以及核对项跨批次提醒策略仍须在 Schema 定稿前收敛。

### 认证与权限

不需要更换认证供应商，也不新增角色体系。核对项必须继承导入批次和交易的资源归属：当前用户只能读取/确认自己有权处理的项目；绑定对象的只读查看权不能转化为确认、编辑或删除对方交易的权限。

## 6. 后续开发顺序建议

1. 完成 API/逻辑模型交叉审阅，尤其是退款来源与原消费的两种关系，以及 ImportReconciliationItem 生命周期。
2. 在真实官方文件验证阶段，确认来源覆盖范围、稳定 ID、来源账户映射和退款字段；不在本阶段预设具体匹配算法。
3. 关闭会改变物理结构或资金守恒的退款边界，再定稿物理 Schema、约束和索引。
4. 独立确定客户端形态、技术栈、数据位置和认证方案，搭建最小工程骨架。
5. 先实现普通收入/支出等最小垂直切片；退款和导入核对按 M4 的独立验收标准实现，不阻塞无关账务功能。
6. 每个功能都要用真实输入和可复现测试验收；文档推演不算软件测试通过。

## 7. 总结

本轮已把新冻结的退款入口和导入后核对行为同步到业务规则、产品功能地图、逻辑数据模型、API 契约、工程模块边界、实施计划和路线图。

**核心产品行为目前已对齐；下游契约尚未完全定稿。** 主要剩余风险是退款资金分配的两个边界、官方退款来源的独立解析动作、导入覆盖范围验证，以及核对项的持久化/重复提醒策略。它们的影响范围和解决时机已在本文列明，不需要重新讨论整套产品，也不应被误当作所有开发工作的共同阻塞项。

## 1. 当前进度

星账仍处于**业务规则已冻结、逻辑模型/API/工程边界候选稿收敛、尚未进入可运行产品功能实现**的阶段。

本轮将用户明确确认的业务决定更新为业务规则 v2.7：

1. 手动记账只允许收入、支出和转账；退款只由官方账单导入创建。
2. 退款到账账户与原消费账户相同；首期不支持信用消费退款。
3. 微信/支付宝官方规则保证退款来源对应唯一原消费。平台专用解析器必须建立唯一关系；若实现解析失败，作为导入错误保留证据，不创建退款交易、不按普通收入入账，而不是让用户在正常流程中猜选原消费。
4. 对完整官方账单范围内未找到来源的手动交易，提供“删除这笔手动账单”或“保留并标记已核对”。
5. 同一来源账户档案与同一手动交易只存在一个核对项；重叠范围复用该项，不重复创建或重复弹出新提示。后续导入成功匹配来源时自动结案。
6. 账户起始日期重建与关系绑定凭据方案按用户要求延后到相关功能实现前，不作为当前文档收敛的阻塞项。

## 2. 真实官方账单核验

本轮重新读取了已提供的两组日期范围账单，核验来源身份、覆盖范围和重叠导入行为。

| 核验项 | 微信 | 支付宝 |
|---|---|---|
| 较宽导出范围 | 2026-08-01 至 2026-09-29 | 2026-08-01 至 2026-09-29 |
| 较窄导出范围 | 2026-08-18 至 2026-09-18 | 2026-08-18 至 2026-09-18 |
| 较宽文件明细行 | 169 | 169 |
| 较窄文件明细行 | 60 | 83 |
| 重叠行交易单号一致 | 60/60 | 83/83 |
| 各文件交易单号空值/重复 | 未发现 | 未发现 |
| 文件头来源账户元数据 | 微信昵称；未见独立不可变账号 ID | 含支付宝账户标识 |
| 文件头覆盖范围与全量导出信息 | 有 | 有 |
| 状态差异 | 重叠样本中核心字段一致 | 5 条交易状态由较早导出的“等待确认收货”变为较新导出的“交易成功” |

**结论：**

- 当前样本支持将官方交易单号作为稳定来源 ID，并结合来源账户档案去重。商户订单号不能替代交易单号作为唯一键，因为它可能为空或重复。
- 导入范围不需要用户手动逐笔填写；应自动读取文件头起止时间和全量导出标记，并核对声明行数与实际解析行数。本次检查的四份文件均满足声明记录数与实际解析行数一致：微信 169/169、60/60；支付宝 169/169、83/83。
- 来源记录身份和来源状态必须分开：同一交易在较新导出中的状态变化应更新当前来源状态，但保留每次 SourceObservation，且不能因此再次入账。
- 支付宝文件头有账户标识；微信文件头当前只显示昵称。因此不能把微信昵称当成不可变的唯一身份 ID，应使用星账内部的 SourceAccountProfile，并只在多个候选档案无法自动判定时要求用户选择。
- 交易行里的“零钱”“银行卡”“花呗”“亲情卡”等是**行级支付渠道**，不是导出文件所属的微信/支付宝账号。二者已在逻辑模型中分开。

上述是对现有样本的初步验证，不等于 M4 导入功能已实现或完整验收。

## 4. 核对项状态与跨批次去重

不建议只在 Transaction 上增加一个简单的 is_checked 布尔字段。核对状态属于“某个官方来源账户与某笔手动交易之间的核对关系”，不属于交易事实本身。

逻辑模型采用 ImportReconciliationItem：

- 唯一范围：source_account_profile_id + transaction_id。
- pending_confirmation：新发现，等待用户处理。
- kept_manual：用户选择保留并标记已核对；之后的重叠导入不重复提示。
- matched_to_source：后续官方来源匹配成功，自动结案。
- 用户选择删除时，调用现有交易删除用例，并在同一事务中关闭/删除核对项，避免悬空引用；不另建回收站或复杂审计系统。
- 相同或重叠日期范围的导入再次检查到该手动交易时，更新最近检查批次，不创建第二个核对项。新提示只针对新建项；既有未处理项仍可从现有账单/导入结果中查看。
- 如果后续官方来源与该手动交易匹配，关联来源并将核对项标记为 matched_to_source，不重复创建交易。
- 只有全量导出标记、起止时间、声明行数和实际解析行数均通过校验，才执行缺失交易核对；否则不能认定“官方账单未找到”。

这比“每个导入批次各存一个已确认状态”更可靠，因为不同批次可能覆盖同一笔交易，单纯的批次状态无法抑制跨批次重复提示。

## 5. 剩余风险与解决时机

### A. M4 开发与真实文件验收前必须验证

| 事项 | 当前决定/状态 | 验收要求 |
|---|---|---|
| 退款与原消费关联 | 业务上保证唯一，规则已冻结 | 用平台专用字段规则逐行验证；解析失败不创建退款交易，不退化为普通收入 |
| 来源单号与状态更新 | 样本已初步验证 | 相同单号重导不重复入账；较新导出更新来源状态，保留每次观察 |
| 覆盖范围完整性 | 文件头有日期范围、全量导出信息和声明行数 | 行数不符、解析失败或非全量导出时，不执行缺失手动交易核对 |
| 来源档案与支付渠道映射 | 已在模型中分开 | 导出账号档案用于来源身份；行级支付渠道映射到星账实际账户/信用来源 |
| 核对项生命周期 | 业务设计已明确 | 验证新建、保留、删除、后续来源匹配、重叠导入和幂等重试 |

### B. 物理 Schema 前必须落实

- SourceAccountProfile 与 SourceRecord 的关联和唯一约束。
- ImportBatch 保存导出时间、起止范围、导出类型、声明行数、解析行数、完整性结果和来源档案。
- SourceObservation 保留每次导入的原始字段/状态，并能区分导出时间。
- ImportReconciliationItem 按来源档案与手动交易唯一，持久化状态与首次/最近检查批次。
- 行级 SourcePaymentMethodMapping 与导出来源账号档案分离。

### C. 按用户要求延后

- 修改账户起始日期时，原子重建 applied / historical_only 状态：相关账户功能实现前处理。
- 原消费早于账户记账起始日期、后续才发生退款时，原消费没有可逆序恢复的当前资金份额；该特例需在实现时处理，但不阻塞普通退款。
- 关系绑定凭据的生成、过期、验证和防重放：关系绑定功能实现前处理。

### D. 仍需独立决策

首期客户端形态、技术栈、数据位置、数据库、认证供应商和开源许可仍需在相应工程阶段决定。本轮业务规则不强制更换技术选型，也不提前指定供应商。

## 6. 文档一致性复核

已对齐的关键边界：

1. 手动记账不能创建退款；编辑普通交易也不能将其改为退款。
2. 官方退款来源与退款交易、退款交易与原消费是两种不同关系。
3. 退款到账账户与原消费账户相同；信用消费退款不在首期范围。
4. SourceAccountProfile 表示导出账号；SourcePaymentMethodMapping 表示行级支付渠道映射。
5. SourceRecord 表示官方文件里的真实来源行；ImportReconciliationItem 表示手动交易未找到对应来源的核对状态。
6. 官方交易单号负责来源去重；不同导出中的状态变化由 SourceObservation 保留，不重复入账。
7. 覆盖范围完整性校验失败时不生成缺失交易核对项。
8. 重叠导入复用同一核对项，用户可以删除手动交易或保留并标记已核对。
9. 文档中已将账户起始日期重建和绑定凭据从当前阻塞项移除，延后至对应功能实施前。

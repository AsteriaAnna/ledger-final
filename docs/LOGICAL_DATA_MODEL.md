# 星账｜逻辑数据模型

**版本：** v0.2  
**阶段：** 逻辑模型设计稿  
**状态：** 候选模型；已完成结构收敛与经典场景桌面推演，待审阅  
**业务基线：** [核心业务规则 v2.5（已冻结）](BUSINESS_RULES_DISCUSSION.md)  
**范围：** 定义核心实体、关系、数据归属与关键不变量；不定义物理数据库 DDL、API 契约或技术栈。

## 0. v0.2 变更摘要

本版依据 v0.1 审查结果收敛结构，不改变已冻结的产品范围和业务规则。

1. 将核心实体从 16 类收敛为 11 类。
2. 将退款关联直接放入 Transaction，不再单设 RefundLink。
3. 将来源与交易的当前关联放入 SourceRecord，不再单设 SourceTransactionLink。
4. 将 AccountOpeningAllocation、TransactionAllocation、FundAllocationAdjustment 收敛为统一的 AccountFundMovement；保留 TransactionAccountEffect，因为“交易关联了哪个账户”与“该交易是否影响该账户余额”不是同一个问题。
5. Account 不再同时保存独立的初始余额金额。初始余额由该账户的初始资金变动合计表示，避免初始余额与初始资金份额成为两份真相。
6. Category 暂作为交易上的分类代码/受控字典值，不在本阶段冻结独立的用户分类实体。
7. 补充交易金额修改、交易类型变更、退款关联、起始日期与重复导入的约束和场景推演。

本版仍是逻辑模型，不是数据库 Schema；不要求采用事件溯源，也不要求建立独立审计日志。

## 1. 设计原则

1. **交易事实、账户关联、资金变动、官方来源证据各司其职。** 它们有关联，但不是同一概念。
2. **账户余额与资金份额均由 AccountFundMovement 推导。** 不再额外维护一份可独立修改的当前余额。
3. 账户持有人、实际保管人、资金归属人、资金性质和操作权限是不同概念。
4. 交易所属个人账本决定谁管理该交易，以及该交易计入谁的个人消费统计；资金分配决定实际由谁的哪类资金承担变动。
5. 官方来源是交易证据，不是第二笔交易。重复导入不能重复入账；删除交易后保留来源证据，并允许重新导入。
6. 第一版不建立花呗/信用卡负债账户，不开发截图识别，不设计解绑和余额不足流程。
7. 金额使用最小货币单位整数（人民币以分为单位）；第一版不处理多币种换算。
8. 以满足已冻结业务规则为准，不为减少实体数量而丢失账户关联、历史交易或资金分配语义。

## 3. 核心实体与职责

| 实体 | 核心字段/概念 | 职责与边界 |
|---|---|---|
| User | 用户 ID、认证主体、显示名称 | 身份与个人数据归属 |
| RelationshipBinding | 两个用户、绑定时间、绑定状态 | 确定关系是否已生效以及是否可只读查看对方；不设计解绑流程 |
| Account | 账户持有人、可选实际保管人、名称、类型、记账起始日期 | 表示银行卡、微信零钱、支付宝余额、现金等实际账户；不单独存储初始余额金额 |
| Transaction | 个人账本归属、类型、时间、金额、商户/说明、分类代码、账务语义、可选原交易 ID | 记录交易事实；当前 v2.5 要求退款创建时关联原消费。R1 提案是否允许空父交易 ID 尚待决策 |
| TransactionAccountEffect | 交易、账户、账户角色、流入/流出方向、金额、影响状态 | 记录交易关联哪个账户，以及该账户影响是否纳入余额计算 |
| AccountFundMovement | 账户、资金归属人、资金性质、带正负号的金额、变动原因、操作分组、可选交易账户影响 | 统一表达初始资金、交易资金分配、退款、转账及手动资金重新分配 |
| MonthlyBudget | 用户、月份、预算金额 | 保存个人月度预算，不与对象共用 |
| ImportBatch | 发起用户、来源平台、文件指纹、导入范围、导入时间 | 记录一次官方账单导入 |
| SourceAccountMapping | 用户、来源平台、来源账户标识、目标账户（可空） | 记住官方来源账户与星账账户的映射；不直接产生账务 |
| SourceRecord | 来源平台、来源账户、稳定外部 ID（如有）、标准化字段（含来源提供的原订单/退款关联 ID）、来源状态、可选当前关联交易及匹配依据 | 表示逻辑上的官方来源记录；一条来源记录最多关联一笔星账交易。外部原订单 ID 不等于星账内部 Transaction ID |
| SourceObservation | 导入批次、来源记录、行号、原始字段 | 保留某次导入实际观察到的原始证据 |

### 不再独立建模的概念

- **RefundLink：** 合并到 Transaction 的可选原交易 ID。只有退款交易允许填写；一笔原消费可关联多笔部分退款。
- **SourceTransactionLink：** 合并到 SourceRecord 的当前关联交易及匹配信息。
- **AccountOpeningAllocation、TransactionAllocation、FundAllocationAdjustment：** 合并到 AccountFundMovement，以变动原因区分初始分配、交易分配和手动重新分配。
- **Category：** V1 仅保留分类代码和受控分类字典，不先设计独立的用户自定义分类管理实体。若后续确认需要自定义分类，再扩展。
- **余额与统计快照：** 不在本模型中把当前余额、当前资金份额、月度花销或预算剩余额作为独立账务真相；它们由交易和资金变动计算。

## 4. 账户、初始余额与资金份额

### 4.1 初始余额只保留一份真相

Account 保存每个账户自己的记账起始日期，但不另存一个可独立编辑的初始余额金额。

- 账户初始余额由该账户所有初始资金变动记录的金额合计表示。
- 初始资金变动均为正数，并分配到合法的资金归属人与资金性质组合。
- 初始资金变动的生效日期为该账户的记账起始日期。
- 编辑初始余额时，必须同步修改初始资金分配；分配合计始终等于初始余额。
- 不额外建设用户可见的初始余额审计界面。

因此，不会出现 Account.initial_balance 是 ¥5,000，但初始资金份额合计只有 ¥4,800 的双重真相。

### 4.2 允许的资金份额

每个实际账户内，V1 允许的资金份额组合为：

1. 账户持有人的流动资金。
2. 账户持有人的存款。
3. 绑定对象的存款（仅绑定后允许）。

不允许把绑定对象的流动资金分配到另一方持有的账户。实际保管人不因此获得写权限。

### 4.3 AccountFundMovement 的统一职责

每条 AccountFundMovement 至少表达：

- 发生变动的实际账户；
- 资金归属人；
- 资金性质（流动资金/存款）；
- 带正负号的金额：正数增加该份额，负数减少该份额；
- 变动原因；
- 所属操作分组；
- 如由交易账户影响产生，则关联对应的 TransactionAccountEffect；
- 生效日期。

变动原因至少能区分：初始资金、交易影响、金额修改差额、交易类型变更、真实退款、内部转账、手动资金重新分配。它们是同一实体的不同原因，不要求为每种原因建立一张表。

同一操作可以产生多条资金变动。例如，手动把 ¥500 从自己的存款改为流动资金，会在同一账户和同一操作分组中产生存款 -¥500、流动资金 +¥500 两条记录，净变化为零。

本模型不要求每次交易编辑都保留不可变的事件历史；它要求当前有效资金变动正确，并能识别必要的变动原因。交易编辑只调整该笔交易关联的有效影响，不自动重算后续所有交易。

### 4.4 余额与份额计算

**账户当前余额 = 该账户全部有效 AccountFundMovement 金额之和。**

**某账户内某归属人、某资金性质的当前金额 = 匹配该账户、归属人与资金性质的有效 AccountFundMovement 金额之和。**

关键约束：

1. 同一账户所有资金份额合计必须等于账户当前余额。
2. 账户内的手动资金重新分配，正负变动合计必须为零。
3. 对状态为 applied 的 TransactionAccountEffect，其关联资金变动的带符号金额合计必须等于该账户影响的带符号金额。
4. 对状态为 historical_only 的 TransactionAccountEffect，不生成资金变动记录。
5. 不允许单纯改变资金归属或性质来增加、减少账户总额。
6. 金额使用整数分，不使用浮点数保存。

### 4.5 记账起始日期与历史交易

每个账户独立设置记账起始日期。

- 交易发生在账户起始日期之前：正常保存交易事实，并保留该交易与账户的关联；对应 TransactionAccountEffect 标记为 historical_only，不生成 AccountFundMovement。
- 这类交易仍可在账单中查询，也按已冻结的交易日期规则参与相应历史消费统计。
- 交易发生在起始日期当日或之后：按交易类型正常生成有效账户影响和资金变动。
- 转账两端账户的起始日期可能不同，因此两端的账户影响状态可能不同：交易层仍记录等额转出/转入，早于某一账户起始日期的那一端不产生该账户的余额变动。这符合“每个账户独立确定余额起点”的规则；该账户的初始余额应反映其起始日的实际金额。

## 5. 交易事实、账户影响与资金变动

### 5.1 Transaction 与 TransactionAccountEffect 的分工

Transaction 记录真实交易事实；TransactionAccountEffect 记录交易涉及的实际账户；AccountFundMovement 记录账户内各资金份额实际如何变化。

三者不要求一对一：

- 普通收入通常对应一个账户流入影响。
- 普通支出通常对应一个账户流出影响，并可拆成多条资金份额变动。
- 内部转账对应转出、转入两个等额账户影响。
- 真实退款对应退款到账账户的流入影响，并通过原交易 ID 关联原消费。
- 信用消费计入消费统计，但不生成受管理现金账户的余额影响。
- 信用还款生成实际付款账户的流出影响，但不再次计入消费统计。

TransactionAccountEffect 的金额用于明确该交易对该账户的业务影响，并校验关联资金变动的合计；账户当前余额不直接对 TransactionAccountEffect 求和，而由 AccountFundMovement 计算。

### 5.2 账户影响状态

TransactionAccountEffect 需要区分：

- **applied：** 该账户影响已纳入余额计算，并且存在金额相符的资金变动。
- **historical_only：** 交易与账户的关联保留，但交易发生在该账户的记账起始日期之前，不生成资金变动。

信用消费没有受管理现金账户影响，因此不为其伪造一个现金账户影响记录；通过 Transaction 的账务语义表达其属于信用消费。

### 5.3 普通收入、普通支出与内部转账

- 普通收入默认增加当前账本用户的流动资金。
- 普通支出按已冻结顺序扣减：自己的流动资金 → 自己的存款 → 对象的存款。
- 只有流动资金可以直接参与内部转账；转入侧保持转出侧的资金归属人与流动性质。
- 内部转账的两项 TransactionAccountEffect 金额必须相等、方向相反；在两端均纳入余额计算时，两端对应资金变动也必须等额相反。
- 转账不计收入或消费。
- 不通过普通写操作绕过对象账本的只读权限。当前模型不定义一个操作同时修改另一用户账本的转账流程；如未来确有此需求，需另行设计显式关联方式。

### 5.4 信用消费与还款

第一版不建立花呗/信用卡负债账户，也不追踪欠款余额。

Transaction 保留内部账务语义，用于区分普通交易、信用消费和信用还款：

- 信用消费属于消费统计，但没有受管理现金账户的流出影响。
- 信用还款减少实际付款账户余额，但不计为消费。
- 信用消费与信用还款均不要求建立虚构的负债账户。
- 微信、支付宝官方文件的具体字段映射在导入实现阶段用真实样例验证。

## 6. 交易修改、退款与删除约束

### 6.1 修改交易金额

修改金额只处理差额，不自动重算后续交易：

- 金额增加：只为增加的差额追加扣款，遵循流动资金 → 自己的存款 → 对象的存款。
- 金额减少：只返还减少的差额，检查该笔交易造成的资金份额缺口，优先补对象存款缺口，再补自己的存款，最后补流动资金。
- 差额返还可表现为 AccountFundMovement 中的正向资金变动；它仍属于原交易的修改影响，不应被统计为一笔新的普通收入。
- 当前交易的账户影响金额与其关联资金变动合计必须保持一致。

### 6.2 真实退款

- 退款交易必须关联一笔原消费；原消费可关联多笔部分退款。
- 退款按原交易实际扣款顺序的逆序恢复资金份额。
- 每次只恢复尚未退回的份额，不重复恢复已退回金额。
- 累计关联退款不得超过原消费金额。
- 若编辑原消费金额会导致累计退款超过新的消费金额，必须阻止产生不一致状态；不能静默保留超额退款。具体提示文案属于后续 API/UI 契约阶段。
- 退款到账账户与原消费账户的关联分别记录；不得只因金额、日期或商户相似就把退款静默关联到错误的原消费。

**待决策 R1：** 当前 v2.5 要求退款必须关联原消费；是否允许先保存未关联退款、以及如何表示实际到账但尚未确定归属的金额，尚未批准。若采用审查报告中的建议，需要明确“账户总额 = 已分配资金份额 + 待分配金额”，并在关联成功时原子地把待分配金额转换为退款资金份额。该规则会改变现有份额守恒不变量，因此在决定前不得直接进入物理 Schema。详见 [跨文档一致性与退款闭环审查](CONSISTENCY_AUDIT_2026-10-24.md)。

### 6.3 修改交易类型

- 修改类型时，只处理该交易自身的账户影响与资金变动，不重算其他交易。
- 改为转账时必须明确转出、转入账户，并遵守只允许流动资金直接转账的规则；系统不得擅自把存款改成流动资金。
- 如果该交易已有退款关联，类型修改不能留下“退款关联到非消费交易”的非法关系。模型必须执行完整性检查；不在本阶段扩展复杂的用户流程。
- 转账、退款和信用还款的统计语义不能仅根据金额正负推断，必须按交易类型及账务语义处理。

### 6.4 删除交易

- 删除交易时，该交易不再参与正常余额与统计计算。
- 删除一笔消费时，同时删除其关联退款。
- 与被删除交易关联的 SourceRecord 保留，但清空当前关联交易及匹配状态；后续重新导入允许重新创建或关联交易。
- 不提供账户删除，不设计用户可见的作废流程或回收站。

## 7. 官方来源、导入批次与去重

### 7.1 三层职责

- **ImportBatch：** 一次导入操作的上下文，包括来源平台、文件指纹、范围和时间。
- **SourceObservation：** 某次导入实际读到的原始行和字段。
- **SourceRecord：** 逻辑上的来源交易身份、标准化字段、来源状态及当前关联交易。

两种关联不能混为一谈：SourceRecord 的当前关联交易表达“这条官方来源对应哪一笔星账交易”；Transaction 的原交易 ID 表达“这笔退款属于哪一笔原消费”。来源中保存的原订单外部 ID 是第三种证据，不是内部交易 ID。完整导入流程应先解析整个批次，再解析原单引用并匹配/创建原消费，最后处理退款关联，不能依赖 Excel 行顺序。

同一来源记录可以在多个导入批次中被观察到；一次导入包含多条来源记录。来源证据不直接修改账户余额，只有经过统一交易处理后产生的有效资金变动才影响余额。

### 7.2 去重约束

- 有可靠稳定外部 ID 时，可按“平台 + 来源账户 + 外部 ID”识别同一来源。
- 没有可靠稳定 ID 时，不得只凭金额、日期、商户相同就静默认定为同一笔交易。
- 对文件内容指纹完全相同的重复导入，可识别为已处理批次并避免重复执行。
- 没有稳定 ID、文件内容也不同且无法唯一匹配时，不得伪装成确定匹配；必要时才要求用户处理。
- 一个 SourceRecord 最多关联一笔 Transaction；一笔 Transaction 可以关联多条来源证据。
- 删除交易时解除当前关联，但保留来源证据。来源记录保留不等于永久禁止重新导入。
- SourceAccountMapping 只减少重复选择，不独立产生账务或替用户确认交易类型。

## 8. 统计、预算与权限

### 8.1 统计和预算

- 消费统计与个人预算根据 Transaction 的交易类型、账务语义、交易日期和退款关联计算，不根据资金归属份额推断消费归属。
- 交易所属个人账本决定该交易计入谁的个人消费统计；对象的消费不占用当前用户预算。
- 退款关联原消费后，修正原消费所在月份的花销，而不是退款实际发生月份的花销。
- 内部转账与信用还款不重复计入消费。
- 首页总资金、存款、流动资金以及绑定后的双方四类资金展示，从统一账户和资金份额结果计算，不单独维护第二套余额。
- MonthlyBudget 按用户和月份保存；每个用户独立管理自己的预算。

### 8.2 双人关系与写权限

- 绑定关系决定是否允许只读查看对方账户与账单。
- 账户持有人决定账户归属；实际保管人不自动获得写权限。
- 资金归属人可以不同于账户持有人，但资金归属不自动授予对该账户或交易的编辑权限。
- 前端隐藏按钮不构成权限控制；后端必须拒绝对方账本的新增、编辑和删除。
- 不设计解绑流程，不新增复杂的访客或多层角色体系。

## 9. 经典场景一致性推演

以下为基于冻结业务规则进行的逻辑推演，不代表代码已经实现或通过运行测试。

| 场景 | 输入 | 预期结果 | 模型检查 |
|---|---|---|---|
| 初始余额分配 | 起始日为 10 月 1 日，初始资金份额合计 ¥5,000 | 初始余额由初始资金变动合计得出，不另存一份初始余额 | 通过 |
| 起始日前历史消费 | 9 月 29 日消费 ¥20，账户起始日为 10 月 1 日 | 保存交易与账户关联；账户影响为 historical_only，不生成资金变动；历史消费统计仍可计算 | 通过 |
| 普通支出跨份额 | 份额为流动 ¥100、自己的存款 ¥100、对象存款 ¥100；消费 ¥250 | 扣后为流动 ¥0、自己的存款 ¥0、对象存款 ¥50；账户余额 ¥50 | 通过 |
| 修改金额减少 | 上例消费由 ¥250 改为 ¥150；对象存款缺口为 ¥50，自己的存款缺口至少 ¥50 | 返还差额 ¥100：先补对象存款 ¥50，再补自己的存款 ¥50；最终份额合计与账户余额均为 ¥150 | 通过 |

| 内部转账 | 转出 ¥100，转出资金为流动资金 | 产生等额转出、转入账户影响；只转流动资金，不计收入或消费 | 通过 |
| 转账跨账户起始日期 | 转账发生时，转出账户已进入记账期，转入账户尚未进入记账期 | 两端交易影响仍等额；起始日前的转入端不生成资金变动，其起始余额反映该账户起始日的实际金额 | 通过，遵循各账户独立起始日期 |
| 信用消费与还款 | 信用消费 ¥200，之后从银行卡还款 ¥200 | 消费进入消费统计；消费时不扣银行卡余额；还款扣银行卡余额但不重复计入消费 | 通过 |
| 删除消费并重导 | 删除一笔已关联官方来源的消费及其退款，再导入官方文件 | 删除相关交易及退款的账务影响；来源证据保留并解除关联；后续导入允许重建交易 | 通过 |
| 重复导入 | 相同来源重复导入 | 不重复创建交易；有稳定 ID 按来源身份识别，无稳定 ID 时不使用弱字段静默合并 | 通过 |
| 已有退款后修改原消费类型 | 原消费已有退款关联，用户尝试把它改成转账 | 必须阻止非法的退款—原消费关系，不留下关联到非消费交易的退款 | 完整性约束可表达；提示和交互留待契约阶段 |
| 双人只读查看 | 双方已绑定，尝试从当前用户会话修改对象账单 | 可查看对方数据，但后端拒绝对方账本的写入 | 模型约束明确，运行时权限需在 API 层验收 |

### 推演结论

- 初始余额、资金份额和当前账户余额不再是重复维护的三套数据。
- 交易、账户影响与资金变动分层后，能表达历史交易不影响余额、信用消费不扣现金账户，以及金额修改只处理差额。
- 退款、转账、来源重导入和双人只读边界均有明确关系与不变量。
- 原消费金额被改到低于累计退款金额时，必须阻止不一致状态；该验证是既有“累计退款不得超过原消费”的直接约束。
- 上述结论为逻辑模型推演，不等于数据库、API 或软件功能已通过运行测试。

## 10. 与既有文档的关系及未纳入范围

### 10.1 与业务规则 v2.5 的关系

本模型落实已有规则，不重新定义产品行为。尤其保留：

- 账户初始余额与记账起始日期按账户分别设置；
- 资金份额与账户总额一致；
- 支出、金额修改和真实退款使用各自已确认的资金处理顺序；
- 内部转账只允许流动资金直接参与；
- 信用消费与还款使用不同的统计和现金账户影响；
- 删除消费时删除关联退款，但保留来源证据并允许重新导入；
- 绑定后只读查看对方数据，个人预算仍然独立。

### 10.2 明确不由本模型擅自确定的事项

- **代对象记账及消费受益人：** 当前冻结规则以交易所属个人账本决定个人统计归属；没有另外定义“付款人、账本管理人、消费受益人”三者分离的功能，本期不自行扩展。
- **跨个人账本转账：** 当前权限规则不允许普通操作绕过对方账本的只读权限。本模型不宣称支持一次操作同时修改双方账本。
- **起始日前原消费的后续退款：** 原消费没有当前账户资金变动可供逆序恢复，具体资金归属处理暂留为边界，不在此增加复杂流程。
- **没有稳定外部 ID 的模糊匹配：** 不静默合并；使用真实官方账单验证具体匹配能力。
- **截图识别、负债账户、余额不足/透支、解绑、多币种：** 不纳入本期模型。

# 星账｜跨文档一致性与退款闭环审查

**审查日期：** 2026-10-24  
**审查范围：** 产品功能地图、冻结业务规则、逻辑数据模型、API 契约、工程模块边界、实施计划、路线图与 README  
**状态：** 审查记录；不自动批准新的业务规则  
**代码状态：** 本次只审查和修订设计文档，没有修改产品代码，也没有把设计推演写成运行测试通过。

## 1. 当前进度判断

星账仍处于产品与工程设计准备阶段。已建立产品功能地图、业务规则 v2.5、逻辑数据模型 v0.2、API 契约 v0.1、工程模块边界、实施计划和路线图。

当前问题不是缺少更多通用架构文档，而是部分关键业务边界还没有贯穿“用户输入 → 交易事实 → 账户影响/资金分配 → 官方来源匹配 → 统计”的完整生命周期。现在发现并处理这些问题，正好可以避免物理 Schema 和 API 落地后的返工。

## 2. 真实账单证据与证据边界

可访问的既有复现报告：star-ledger-real-import-review-20261004.md。其测试对象是旧版 star-ledger2 的实际导入流程，不是本仓库 ledger-final 的已运行实现。本轮检索恢复了报告，但没有找到原始两份 Excel 的可直接读取副本；以下数字来自该报告，不声称本轮重新读取原始工作簿。

| 真实样例发现 | 复现结果 | 对设计的含义 |
|---|---|---|
| 微信账单 | 169 条；12 条退款/退回记录中，9 笔消费退款已自动关联，另 3 笔是转账退回，未关联 | 必须区分消费退款与转账退回，不能都要求原消费作为父交易 |
| 支付宝账单 | 169 条；21 笔退款，旧流程自动关联 1 笔 | 不能把旧流程的低自动关联率误判成来源数据没有匹配依据 |
| 支付宝原消费可用性 | 19 笔原消费在同一文件中，另 2 笔不在文件中 | 对同批可识别的原消费可以自动关联；缺少原消费证据时必须保留待关联状态 |
| 订单号前缀试算 | 对额外 18 笔退款使用真实原始编号前缀寻找唯一原消费，纯内存账务试算全部通过 | 编号标准化与原单识别是可修复的确定性规则问题；不应让用户逐笔从大量候选中搜索 |
| 来源匹配体验 | 退款候选列表曾出现 137 条等大量候选，且部分未关联退款没有对应处理入口 | 匹配证据必须传递到界面；不确定时提供少量有依据的候选，而不是把全量交易列表交给用户 |
| 提现与零手续费 | 3 笔微信提现中，2 笔的付款/到账方向错误，1 笔合法零手续费被判为手续费缺失；另有 29 条来源支付方式为“/”的记录没有得到恰当的账户处理 | 对受支持的真实样例，这些是导入正确性要求，不应以“低频特殊交易”为由跳过 |

报告还记录了同一文件重导未重复入账，但账户问题重评估和退款候选呈现仍有缺口。以上数据可作为后续回归基线；新实现必须重新运行真实文件验收。

## 3. 关键缺口与待决策项

### R1｜手动退款能否先保存、后关联原消费

**当前文档状态：** 业务规则 v2.5 与 API 契约要求退款关联原消费；产品功能地图的手动记账字段列表没有退款类型。当前方案尚未完整支持“先记录真实退款，后通过官方账单补关联”的闭环。

**建议方案（待用户确认，不属于已冻结规则）：**

1. 手动录入允许选择“退款”，输入实际到账金额、时间、实际到账账户和可选商户/备注；原消费暂时未知时，不强迫用户先搜索原消费。
2. 未关联退款仍是退款，不得暂时伪装成普通收入；它不立即冲减某个月的消费统计。
3. 实际到账金额应立即反映在实际到账账户总额中。由于原消费的资金份额尚未确定，金额先进入明确标识的“待分配/待关联退款”部分，不归入任何人的流动资金或存款。
4. 为维持资金守恒，建议将账户不变量明确为：**账户总额 = 已分配资金份额合计 + 待分配金额**。退款完成关联后，在一个原子操作中将待分配金额转换为按原消费实际资金分配逆序恢复的资金份额。
5. 待关联退款不计为收入；完成关联后，按原消费发生月份修正消费统计。若无法唯一匹配，继续保留待关联状态，不猜测、不丢弃、不重复入账。

此方案比“先把退款当普通收入、以后再改”更准确，但会改变当前“所有账户余额必须完全由已分类资金份额构成”的不变量，因此必须先确认再设计物理 Schema。

### R2｜两种关联关系必须明确分开

需要分别表达：

- **来源关联：** 一条官方 SourceRecord 是否对应一笔星账 Transaction。
- **退款父子关联：** 一笔退款 Transaction 对应哪一笔原消费 Transaction。
- **来源中的原单证据：** 例如支付宝退款编号所含的原订单候选 ID；这是外部 ID，不等于星账内部 Transaction ID。

当前 API 的 link_existing_transaction 只定义了来源记录与已有交易的关联，不能自动代表退款已关联到原消费。模型和 API 必须明确区分这两条关系。

**建议的导入顺序：** 先解析整个文件并保存来源记录，再建立所有可靠的外部原单引用；匹配或创建原消费；最后处理退款父子关系。流程必须不依赖原消费行和退款行在 Excel 中的先后顺序。若原消费记录已被手动记账创建，应先将官方来源关联到该笔手动消费，再把退款关联到它。

### R3｜微信转账退回不能按消费退款处理

真实样例中的 3 条转账退回不能被强制关联到 expense。在实现完整官方导入前，需要确认它们的领域表达方式：建议作为与原转账关联的转账冲回/退回，反向恢复原转账的两端资金影响；不得计为消费退款或普通收入。具体来源字段与原转账可匹配证据必须用真实行验证。

### R4｜三个退款边界仍需单独决定

- **退款到账账户与原消费账户不同：** 资金应计入真实到账账户；待明确如何在到账账户内恢复原消费的资金归属和性质。
- **原消费为信用消费：** 原消费没有现金扣减份额，不能直接套用逆序恢复现金份额。
- **原消费发生在账户记账起始日期之前：** 原交易没有该账户的有效资金变动可供逆序恢复。

这些问题阻塞各自相关退款组合的完整实现和验收，但不阻塞账户管理、普通收入/支出等无关功能，也不要求先决定认证供应商或客户端框架。

### R5｜受支持的真实账单中的提现与零手续费必须正确处理

旧版复现报告明确记录：3 笔微信提现中，两笔付款/到账方向被解释反了，另一笔合法零手续费提现因零值解析失败而未入账；29 条支付方式为“/”的来源记录也未得到恰当账户处理。

这与业务规则中“提现、手续费等低频特殊交易暂缓”的概括性表述存在范围歧义。统一后的规则应为：**不在首期支持范围或真实样例中的罕见变体可以暂缓；但出现在本期承诺支持的官方账单样例中的交易，必须正确解释方向、账户角色与合法零值，才能通过导入验收。**

## 4. 文档一致性审查结果

| 文档 | 已发现问题 | 需要的统一处理 |
|---|---|---|
| PRODUCT_FUNCTION_MAP.md | 手动记账类型遗漏退款；统计比较说明与已冻结的日均变化率公式不一致 | 补齐退款类型；统计口径以业务规则 v2.5 为准；关联 R1 待决策 |
| BUSINESS_RULES_DISCUSSION.md | 冻结规则要求退款创建时必须关联原消费，但没有记录新的“先保存、后关联”变更提案；对转账退回的领域边界未明确；此前将提现/手续费整体列为暂缓，与真实样例验收范围不清 | 保持 v2.5 不被静默改写，将 R1/R3 标为待确认业务决策；明确受支持样例中的提现方向、零手续费和账户角色必须通过验收 |
| LOGICAL_DATA_MODEL.md | Transaction.original_transaction_id 的“可选”与“退款必须关联”缺少适用条件；没有明确外部退款原单 ID 与内部父交易 ID 不同 | 标清当前约束与 R1 待决策；明确 SourceRecord 的原单证据与两类关联 |
| API_CONTRACT.md | 创建退款示例要求原消费 ID；没有完整描述未关联退款状态/待分配金额；导入 resolution 只明确来源关联 | 在 R1 决策前声明当前契约限制；后续补充创建、关联和原子更新契约 |
| ENGINEERING_MODULE_BOUNDARIES.md | 统一账务入口已明确，但退款待关联状态、来源关联与父子关联的协作尚未定义 | M3 管理退款父子关系与账务影响；M4 管理来源证据与匹配；共享规则统一验证 |

| ROADMAP.md | 未单列 R1/R3；更新日期需与本轮审查一致 | 保留核心范围冻结，列出退款和转账退回待决策项，更新日期 |

另一个已发现的文档冲突是：产品功能地图曾建议比较本月至今与上月同期，但冻结业务规则明确采用“本月截至今天的日均花销”与“上月全月日均花销”比较。产品功能地图应服从冻结业务规则，而不是保留第二套统计口径。

| 领域 | 是否受影响 | 判断 |
|---|---|---|
| 业务规则与流程 | **是** | R1/R2/R3 会改变退款输入、待关联、匹配和统计修正流程，需先形成明确决策 |
| 逻辑数据模型与物理存储 | **是，且必须在 Schema 前解决** | 是否允许空父交易 ID、待分配金额、外部原单证据和关系状态会影响字段、约束与索引 |

| 模块边界 | **需要补充，不需推倒重来** | M3 仍负责交易与账务；M4 仍负责来源解析和匹配；要明确两者的调用顺序与事务边界 |
| 技术选型 | **不改变具体选型方向** | 不要求特定数据库或框架，但存储必须支持原子事务、引用约束和可靠的唯一性检查；这本来就是既定要求 |
| 认证方案 | **不改变** | 不需要新认证供应商或登录流程；但退款与来源关联操作必须校验所有相关交易、来源和账户均属于当前用户可操作的数据范围 |
| 产品 UI | **需要补齐** | 手动退款需支持暂存；导入结果应区分已关联、待关联和有歧义，不建设复杂异常中心 |
| 真实账单覆盖 | **需要补齐** | 受支持样例中的提现方向、零手续费和未知支付方式必须有正确的入账/待处理结果，不能把它们统一标为非阻塞边界 |
| 测试与交付 | **必须补齐** | 需用原始 338 条真实账单复测，且新增手动退款先行、原消费先行、行顺序颠倒、重复导入、原单缺失、转账退回等场景 |

## 6. 推荐处理顺序

1. **先确认业务决策：** 是否允许未关联退款；待关联期间如何展示到账金额和资金归属；微信转账退回怎样表示。
2. **更新并统一业务规则：** 若 R1 被接受，明确修改业务规则版本，而不是把新行为悄悄写进 API。
3. **更新逻辑模型：** 定义退款父子关系、来源关系、待分配金额和守恒约束。
4. **更新 API 契约：** 明确创建未关联退款、后续关联、导入自动匹配和关联失败的行为。
5. **确认技术方案并设计物理 Schema。** 不在退款核心不变量未定时冻结数据库结构。
6. **先完成最小可运行的手动记账/退款切片，再完成官方账单关联闭环。** 每一步都可运行验收，避免把所有功能都拖到最后。
7. 以原始 338 条真实账单作为验收基线；同时验证提现付款/到账方向、合法零手续费和“/”来源的处理结果。

## 7. 后续验收条件

- 手动记录未关联退款后，实际到账账户总额正确变化，退款不被记为收入，待分配金额清晰可见。
- 官方退款来源能与已存在的手动退款匹配时，只增加来源证据，不重复创建退款或重复改变余额。
- 原消费也为手动记录时，系统先可靠匹配原消费，再建立退款父子关系；无法唯一匹配时保留待关联状态。
- 支付宝真实编号可按有依据的规则提取原单候选；唯一匹配且未超退时自动关联，不能唯一匹配或原单缺失时不猜测。
- 同一文件的行顺序变化不改变最终匹配结果；重复导入不重复入账。
- 微信消费退款与转账退回走不同的账务规则。
- 退款关联成功后，账户总额、已分配资金份额、待分配金额、原消费月份统计均一致。
- 不同到账账户、信用消费退款、起始日前消费退款和部分/多次退款有明确规则及成功/失败测试。
- 受支持真实账单中的提现方向正确、合法零手续费不会被当作缺失值；“/”来源不被无依据绑定到错误账户。

**本审查不批准任何尚未确认的新业务规则，也不表示功能已实现。** 当前最重要的产出是明确返工风险与决策顺序；在 R1/R2/R3 形成决策前，不应冻结退款相关物理 Schema。

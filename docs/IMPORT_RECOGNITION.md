# 星账｜导入识别机制：独立退款

**日期：** 2026-10-24  
**业务基线：** v2.8  
**状态：** 产品规则已确认；真实样本字段与统计实验完成，正式导入/账务未实现或验收。

## 1. 这次改变什么

退款由官方来源独立创建为refund，不关联原消费。取消退款原单匹配算法、original_transaction_id、原消费累计退款上限、按原扣款份额逆序恢复及消费删除级联退款。

保留官方来源到退款自身的关联、来源身份去重、来源观察历史、删除后可重导、手动记账不开放新建退款等规则。来源去重与退款原消费关联是两回事；取消后者不取消前者。

## 2. 按星账需要提取信息

| 目标 | 读取/判定规则 | 结果边界 |
|---|---|---|
| 平台与表头 | 根据文件标题、交易时间及交易类型/交易分类等列名识别，不写死行号 | 声明行数与实际读取数核对 |
| 来源身份 | 平台+内部来源账号档案+完整官方交易单号 | 清理本样本单号末尾制表符等空白（实验也兼容字面量\\t）；不转为数字、不截断退款单号 |
| 金额 | 微信金额(元)、支付宝金额，转整数分 | 按用户确认：行金额即实际金额变动；支付红包不另扣、不反推原价 |
| 账户 | 明确到账状态优先；普通支付从支付方式读取；剥离支付优惠标记 | 已存入零钱→微信零钱；银行卡名称/尾号是映射线索，不是内部Account ID |
| 退款 | 微信交易类型含退款；支付宝退款成功状态 | 先区别退款行与原消费状态变化，累计退款状态不生成额外流水 |
| 退款子类型 | 微信转账-退款→transfer_return；商户退款→merchant_refund | 商户退款默认抵减，转账退回默认不抵减；不明类型明确待处理 |
| 有效性 | 失败/关闭不产生有效账务；等待确认收货保留已发生的支出 | 不以收货完成为付款发生前提 |
| 时间 | source_occurred_at保存官方原始时间；occurred_at默认同值 | occurred_at可编辑，用于记账及统计；原始时间不覆盖 |
| 抵减 | affects_spending:boolean，仅refund使用 | 用户可编辑；开关不改变到账金额，退款不计普通收入 |

亲情卡、花呗消费及还款排除本轮样本验证，单列数量与行号；不能作为已成功识别入账。该实验范围不自动宣称整个产品已完成负债处理，也不借此扩大负债账户范围。

微信普通红包收发是交易，支付宝支付红包是优惠，不能仅凭“红包”二字将两者一起过滤。

明确状态与账户字段冲突时，保留证据并报告冲突；不把所有空支付方式都填成微信零钱。账户映射确定后复用；同张银行卡跨平台可映射同一Account，但尾号不作为全局唯一ID。

## 3. 独立退款的处理

1. 提取官方来源ID、到账账户线索、金额、退款时间及子类型。
2. 按来源身份去重；来源账号档案及实际账户映射仍是正式入账前提。
3. 无需原消费，创建独立退款；实际账户流入为行金额。
4. 商户退款affects_spending=true；转账退回默认false。两者均不计普通收入。
5. 按退款自己的occurred_at所在月计算抵减；净花销=计入消费的支出−该月启用抵减的退款。净花销可为负，不擅自截断为0；预算、日均及预测沿用同一口径。
6. 用户可编辑记账日期和抵减开关；重导不能静默覆盖这两项，不因编辑日期产生新的来源身份。
7. 删除消费不删除退款；删除退款只撤销自身影响。删除后的来源可在再次导入时恢复对应独立交易。

例：8月支出100元，9月退款30元，默认8月花销100元，9月抵减30元。将退款记账日期改至8月，则8月净花销70元，9月不再抵减。关闭抵减则只保留实际到账，不抵减任何月份。

### 余额与资金份额边界

- 抵减开关只影响统计，不增加或减少实际到账额。
- 改日期不跨账户起始日时，当前退款流入金额不变；跨起始日时按现有historical_only/applied规则切换本交易余额影响，必须原子处理。保留官方原始时间供回查。
- 不读取原消费扣款份额。退款按统一入账回补规则处理；“先补对象存款、再自己存款、再流动资金”的顺序不能单独定义缺口金额。具体缺口基准仍待资金份额实现前明确，本轮不伪造目标存款额，也不宣称资金归属已经验收。
- 修改日期不自动重算后续全部交易的份额；当前交易影响及统计按统一编辑规则更新。

## 4. 本次实测结果

使用两份2026-08-01至2026-09-29官方XLSX；原始账单和含个人明细的报告不提交此仓库。实验脚本：[verify_import_recognition.py](../experiments/verify_import_recognition.py)。仅在已提供的样本范围验证，不声称平台所有版本均已覆盖。

| 阶段 | 微信 | 支付宝 | 合计 |
|---|---:|---:|---:|
| 声明/实读行数 | 169/169 | 169/169 | 338/338 |
| 排除亲情卡/花呗相关 | 0 | 123（99+24） | 123 |
| 纳入范围 | 169 | 46 | 215 |
| 退款/退回行 | 12 | 1 | 13 |
| 商户退款默认抵减 | 9 | 1 | 10 |
| 转账退回默认不抵减 | 3 | 0 | 3 |

13条退款均提取到账户线索、金额、时间和子类型；没有原消费关联也可形成完整的退款候选。合计退款/退回1706.26元，其中商户退款抵减1486.26元，转账退回220元默认不抵减。以上是退款子集金额，不是整份账单余额或总花销。

| 样例 | 提取结果 |
|---|---|
| 微信第21行 | 从已存入零钱状态取得微信零钱；29条同类状态均可提取 |
| 微信第32、33行 | 分别退款0.44和0.26元，流入合计0.70元；累计状态不重复记账 |
| 微信第26行 | 转账退回15元，实际流入，默认不抵减花销 |
| 支付宝第66行 | 银行卡实际支出40.79元，支付红包仅标优惠 |
| 支付宝第56行 | 独立商户退款40.49元，无需原消费 |

其余纳入行：146条支出字段、3条收入字段、46条微信转入/转出候选、6条充值提现候选、1条关闭记录。后两类转账候选共52条仍需明确实际业务语义/两端账户，不把“字段读取成功”算作“全部可入账”。

14项实验检查通过：完整读取/范围核对、13条独立退款字段、子类型默认值、累计状态不重复计额、状态补账户、优惠拆分、等待收货、关闭不入账、来源重复新增0条、重导保留用户编辑、抵减不改到账金额、跨月日期编辑、消费删除保留退款、起始日边界切换。

重复导入、编辑、删除和日期边界使用实验内存模型；尚未验证数据库事务、真实Account绑定、资金份额、API、并发与云同步。脚本的固定计数断言针对这两份样本，不是通用解析器适配所有文件的承诺。
